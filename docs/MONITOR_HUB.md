`collection-hub-serve`把多个**已经运行的本机采集服务**放进同一张“让排队数据看得见”观察台。用户按名称选择门店，查看号码、原始数量、展示集合变化、响应间隔和缺口；切店与刷新只读取所属工作者的本机HTTP投影，不新增寿司郎查询，不读取运行中的数据库。

当前实际覆盖名单见[十二店配置](../config/collection-stores.json)，运行证据见[分批采集](STORE_EXPANSION.md)和交接历史。目录名称来自此前正常官方响应，目录当前时效、返回身份、源更新时间与数量单位仍未认证；号码展示不等于完整叫号游标，集合消失不等于真实过号。

## 怎样使用

先独立启动采集批次，再在已有0700私有目录保存0600配置；观察台不会创建、恢复或重启采集。每个工作者仍明确负责1–3家店，一个观察台最多16个工作者／48家不重复门店。端点只能是显式`http://127.0.0.1:端口`，拒绝域名、用户信息、路径、外部网卡和重复路由。

```json
{
  "schema_version": 1,
  "deadline_at": "2026-10-10T11:14:18.967Z",
  "workers": [
    {
      "endpoint": "http://127.0.0.1:53001",
      "stores": {"3014": "中关村大融城店", "3004": "西单大悦城店"}
    },
    {
      "endpoint": "http://127.0.0.1:53002",
      "stores": {"2009": "世豪广场店"}
    }
  ]
}
```

示例端口须替换为实际本机采集服务的端口，截止替换为明确未来时间，最长14天；输入上限16KiB。后台查询预算和截止仍由每个工作者独立控制，不因为观察台重开而重置。

```sh
sushiwait collection-hub-serve --config-file /private/local/workers.json --port 51930
```

只绑定`127.0.0.1`。按配置截止退出，关闭观察台也不停止采集工作者；它不是生产云服务器或开机自启。操作者休眠、断网或停止Docker时，采集可能中断，页面不伪造连续数据或补零。

## 状态如何对应

| 本机路径 | 行为 |
| --- | --- |
| `/monitor`、`/monitor.js`、`/monitor.css` | 使用包内原统计资产；资产读取不访问工作者 |
| `/api/v1/status` | 首家店所属工作者状态，同时给出完整选择名单 |
| `/api/v1/stores/{id}/status` | 该店所属工作者的状态、期限和查询计数 |
| `/api/v1/stores/{id}/queue`、`/history` | 该工作者已提交的号码与统计投影 |

查询计数明确是“当前门店所属批次累计”，不是所有批次总和；`active_batch_store_ids`保留实际批次范围，`store_ids`是观察台选择范围。不能用另一批次仍在运行来遮盖所选门店的失败，失败批次也不会阻止切换到正常批次。门店名称用浏览器文本写入，不执行目录内容。

每次页面更新仅读取当前门店的三个本机出口，原5秒页面节奏保持；真实上游背景周期仍为300秒。配置端点和精确运行资料只在本机，不上传模型或公开仓库。观察台读取确实会产生本机网络请求，`upstream_network_performed_by_hub=false`只说明观察台不查询寿司郎；不能把它说成没有任何网络操作。

## 有限读取与核验

工作者读取固定路径，3秒本机超时、2MiB响应上限、不跟随重定向；核对配置批次和返回门店，异店、未知状态或异常声明返回固定失败码。服务不接受POST、请求体、任意查询参数或任意转发路径；不提供微信凭证、个人号单、业务写入或模型调用出口。运行资料与预测结果仍按各自私有规则隔离。

新增检查包括不同批次状态／预算、失败隔离、未知路由无读取、截止无重启、配置范围、响应大小／重复键、实际本机服务及浏览器切店。安装检查会启动安装包里的实际命令、两个合成本机工作者并核对按截止退出；所有寿司郎和供应商请求均为0。合成软件检查不是全国实时覆盖或预测准确率验收。
