# 私有接入窗口与独立关闭的协调

rc12新增本机 `context-window`。它把已安装的独立关闭守护与正常目录暂存接入放在一次协调中，接收结束后通知守护提前关闭，减少人工/控制工具交接等待。**不启用MitM、不打开或登录微信、不恢复域名、不改主配置、不发送上游查询或初始化。** 已安装包的沿用旧上下文负例与关闭已实测；新上下文供应/主提交及整体缺口仍须继续验收，软件检查不替代正常新凭证供应。

```sh
sushiwait context-window \
  --credentials-file /absolute/private/current.json \
  --staged-file /absolute/other-private/staged.json \
  --revision 10 --seconds 40 --collector-paused
```

只支持已安装包、macOS及已观察的Surge CLI。主文件和暂存须显式指定、在不同的私有目录中，初始完整上下文相等，要求新revision严格更高。先在本机准备私有副本，目录0700、文件0600，沿用16KiB/本人所有/单链接/无符号链接的严格读取；不搜索资料、不拼环境配置。另一个私有目录是为了接收器写暂存时不会与主目录锁冲突。主目录的协作独占锁保持到清理和末次核对结束，同目录capture/promotion写者须遵守此锁；它不是全系统Surge锁，不约束不合作操作者。

开始前必须已实际暂停所有相关采集，或当前没有运行中的采集，三个调试开关均OFF，操作者仅准备已有授权的sapi单域名。`--collector-paused`是调用方确认，不是工具认证暂停或名单，ready也明确两项verified=false；工具不会自动停止其他进程或更改安全设置。

工具使用相同已安装Python的隔离入口，启动另一个新会话中的 `surge-guard` 子进程，窗口5–40秒。检查有界ready协议、严格三个OFF、实际未退出与截止仍有效后，正常接收器才报告context_window_ready。操作者必须在此截止前执行已授权正常客户端动作，不能在守护结束后再启用临时解密。原始请求/头与凭证不进入父进程输出；正常目录接收仍只内存处理、固定sapi路径、只提交独立暂存。

接收成功或失败都通知自己的守护进程结束，让它发出OFF并回读；另有40秒独立截止，不依赖父进程返回。守护运行在新会话中，父进程意外死亡后仍有自己的限时关闭流程。父进程读取关闭结果时限制64KiB/8秒，无法确认时不硬杀保护进程、不称关闭成功。完成后再次直接核对三个OFF、目录身份、主上下文未变化与暂存版本/授权/同应用，才返回已确认结果。守护ready读取限制4秒/64KiB，重复键/非有限数、过时或异常协议拒绝。接收没有新上下文时保留固定“未找到/沿用旧上下文”原因，其余错误不输出原文。

暂存原子提交后，即使清理、回读、协作写者或持久化出现问题，也保留该文件，不回退或改主文件。错误报告staging_changed=true/false/null和cleanup_confirmed，不把不知道的状态称未提交。durability=false退出1；正确完成也只是暂存已接入和OFF已确认，server_acceptance仍unverified。操作者还须关闭小程序、恢复原名单，再使用[context-promote](CONTEXT_PROMOTION.md)独立提交主配置；采集实际接受另验。

独立限时保护仍不能覆盖系统睡眠、保护进程被硬杀、Surge不可用或其他操作者再次开启等全部故障；关闭未确认须人工核对，不能继续自动主提交。父进程SIGTERM/硬退出没有成功结果；独立守护仍按自己的截止运行，之后也需核对。缺口不能回填为真实观测，流程是否缩短必须看实际请求时间，不能拿软件设计声称防过号已达标。此前公开主提交流程12份任务的实际282.267秒缺口见E0120。
