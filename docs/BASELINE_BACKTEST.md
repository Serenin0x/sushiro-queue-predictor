# 历史基线的时间顺序检验

候选 rc39 新增 `baseline-backtest`：从截至评估时刻已接收并确认的叫号经历中，重建取号时刻和指定已等待时长的[历史基线](HISTORY_BASELINE.md)，再用叫号区间计算误差与覆盖界。每次重建只使用该预测时刻以前已接收的结果和审核，不把后来补录或纠错倒灌到训练资料。

这是历史研究回放，不能证明当时实际运行过预测；`forecast_log_verified=false`、`model_performance_verified=false`、`verified_training_labels=0`、`eta_available=false`。真实线上预测日志、可训练资格、校准、实时/LLM模型和两种产品模式的完整验收继续原目标。原连续采集和字段核对另有证据，不用软件分数替代实时数据验收。

## 输入与运行

输入是一个明确私有 JSON，最多 16 KiB，精确包含以下字段：

```json
{
  "schema_version": 1,
  "as_of": "2026-10-06T18:00:00+08:00",
  "data_origin": "synthetic",
  "api_profile": "miniapp_gateway",
  "store_id": "900001",
  "minimum_samples": 1,
  "elapsed_seconds": [0, 300, 900],
  "max_cases": 100
}
```

`as_of` 带时区和秒、不得晚于调用时刻，是结果评估截止。来源只允许 synthetic/self_reported，profile 按已有契约隔离；`900001` 为合成 ID，不查询真实门店。`minimum_samples` 为 1–1000 的可计算门槛，不是质量保证。`elapsed_seconds` 为严格递增的 1–16 个整数，范围 0–172800 秒；0 使用新加入基线，正数使用已等待条件基线。`max_cases` 为 1–100，本入口暂用于有界研究；超过可重建案例数量上限就整体拒绝，不静默选择少数成绩好的结果。

```bash
sushiwait baseline-backtest --source-db /private/source/source.sqlite3 \
  --reviews-db /private/reviews/reviews.sqlite3 \
  --input /private/output/plan.json --output /private/output/replay.json
```

两份源库只读，分别完整审计最多 `--max-revisions`（默认/上限 10000）条修订；超限、坏链或未来时钟状态使整个操作失败，不返回部分分数。源库、审核库和输出位于不同既有私有目录。POSIX 目录 0700、输入/输出 0600，原子发布新文件，已有目标不覆盖，输出最多 2 MiB。持久化确认失败显式报告 committed/durability 并非零退出。

终端只输出是否写入、经历和案例数量、固定错误码及未验证状态。具体门店、episode、精确时间、预测、误差和指纹只在私有结果文件；小样本统计也不自动公开或传给 LLM。入口不联网、不查凭证、不控制微信/Surge，也不取号、取消、重排或发送提醒。

## 训练截止和结果截止分别处理

1. 在评估截止 `as_of`，根据[结果首次接收](OUTCOME_INTAKE.md)和[审核首次接收](OUTCOME_REVIEWS.md)选择当前确认的结果版本。过时、冲突、拒绝或证据不足的经历不作为评估真值；合成和人工资料分开。
2. 每个经历的重建预测时刻为“取号区间上界加 elapsed”。这是一项明确的回放约定，不认证当时客户端可用状态，也不把不确定取号时刻伪装成精确实际预测时间。
   目标门店、队列、人数和桌型也从评估截止的审核结果重建，假定它们当时已知；没有实际历史请求证明，`historical_target_context_verified=false`。目标资料后来的纠错可能改变这项重建假设及分数，不能把它当作当时的真实输入或完整防泄漏实证。
3. 只有重建时刻严格早于叫号区间下界才重建。已经可能叫号的案例，按每个 elapsed 单独记录排除数量；不能事后声称它仍然没叫号。
4. 每个重建时刻重新执行基线的双接收截止选择，排除目标 episode，精确匹配门店/来源/profile/队列/人数桌型，并使用当时可知的日历。后来的纠错或审核撤回不会改掉更早的训练状态；发生在重建时刻前的撤回会使该资料失去资格。
5. 没有足够当时历史或肯定存活资料时，保留缺失原因；不补全国平均值或零等待，也不从报表里隐藏这些案例。

例如一段 2020 年经历在 2026 年才首次接收，程序可以在当前研究基线中使用它，但不能把它作为 2020 年其他案例的已知训练资料。安装检查以合成晚接收案例验证这个边界：有结果但历史训练不可用时，计分数量为零，误差为 null。

源库和审核库的私有父目录共享锁在整个回放期间保持，写入者不能同时更改这些文件；所有历史读取继续执行原有完整性检查。当前最多 100 次重建，每次完整审计有界资料；更大数据集的服务端时间索引和批处理仍需后续实现。

## 误差结果如何解释

基线代表点和经验 p10/p90 包络与观察到的叫号区间交给[区间算术](INTERVAL_EVALUATION.md)：误差下界是点到观察区间的距离，上界是到两个端点的最大距离。预测跨度完整包含观察区间才确认覆盖，相交只算可能覆盖；没有用标签中点提高精度。

结果按 elapsed 分开报告样本数、缺失原因、叫号可能已发生的排除数量、误差/覆盖界和区间宽度。相同 episode 在不同 elapsed 中会重复出现，各组不是独立样本，不将它们合并成扩大样本量的整体准确率。每组内一段经历只产生一个案例。

仅接受已有确认声明的叫号结果，尚未处理未叫号、取消、重排等右删失或缺失总体。当前样本可能有人工记录选择偏差，审核不是事件真实性认证；也没有独立训练/校准/最终测试集、真实置信覆盖校准或代表性证明。前向扩大历史窗口检验不是最终产品成绩。

理想用餐时间规划需要保存当时真正输入的到店偏好、实际采取的取号动作和之后结果；本入口不会从事后叫号时间反推出一个“完美理想时间”来包装准确率，`ideal_time_planning_evaluated=false`。这项真实计划记录、反向模式和重排反事实验收仍需实现。

## 保存与继续

私有文件保留每次重建时刻、实际历史输入指纹、用于评估的结果修订/接收依据和区间记录。预测 ID 只是新生成的回放 UUID4，不是认证的生产预测 ID。复现指纹排除随机 ID，包含策略、计划、截止已知输入与实际区间结果；未来补录只改变完整审计诊断，不改变早先截止的回放。

下一步需要正常真实用餐证据、明确可训练资格和实际预测日志，按门店/日型/时段及提前量评估缺失、误差和覆盖，保留尚未完成的全部经历，再决定校准与发布条件。真实长期数据、服务器、实时波动/LLM、防过号、R18后的微信前端及授权业务继续原完整目标。

实时邻域和融合模型另见[实时对照回测](REALTIME_BACKTEST.md)，在同样历史时刻和同样案例上比较；本命令继续保持原纯历史职责。
