## 凭证更新的自动化与人工边界

目标流程是：采集检查保护状态 → 正常客户端更新控制器完成通常操作 → 接入整组新上下文 → 关闭并确认临时调试 → 独立门店查询验证 → 从当下恢复采样。它不应要求本人定时刷新或导出HAR；这些动作是否足以产生新上下文必须依据真实结果，不能把正常页面加载当作更新成功。

| 场景 | 目标处理 | 当前事实 |
| --- | --- | --- |
| 本人微信正常登录、电脑可运行、查询凭证到期 | 控制器自动完成正常更新与独立验证 | 正常客户端新6、新8及两个独立进程各跨到期恢复已实测；全天控制器未实现 |

| 更新超时、仍是旧授权、界面变化、断网 | 保留缺口，停止使用旧值；可恢复条件明确后再继续 | 已有本机保护、首错停止与有界任务重启对账；自动故障处理仍缺 |
| 锁屏、睡眠、系统或客户端升级 | 单独记录运行限制与恢复结果 | 尚未做长期验收，不擅自关闭锁屏保护 |

## 采样与故障处理

- 先固定三家试点，不把147条历史目录当成全国采集许可或覆盖保证。当前collect仍限1–3店、有界运行；常驻和更大批量另行实现。
- 先验证营业时段源变化与允许频率，再确定普通背景周期。用户计划前30分钟的60秒、前15分钟的30秒是产品目标，不意味着全国所有门店全天30秒查询。闭店可停止或低频探测，但必须根据已核验营业状态/恢复条件决定，不能把闭店数据当零等待。
- 有效凭证只读查询、正常更新和上传分别限制请求。未知配额保持未知；禁止为查找上限压测或失效后密集重试。现有collect首错停止、401不重试保持；未来分类恢复须另有实现与测试。
- 更新超时、客户端不可用、断网时记录缺口及状态，停止提供假“实时”结论。恢复后从当下采样，过去没有观测的时间不能补造成真实数据。
- 到期时间逐份记录未验签声明与实际使用表现，不把两份3600秒声明推广成永远固定一小时。门店ID与查询凭证分开处理。

## 逐级长期验收

下列时间均为拟定验收窗口，尚未执行，不是交付期限。每一级要覆盖营业时段，记录实际门店/软件版本/上下文更新次数和缺口，不能只报告总成功率。

| 阶段 | 验证目的 | 必须留下的证据 |
| --- | --- | --- |
| 24小时三店 | 多轮正常凭证更新与营业/闭店切换 | 实际更新次数、更新耗时、每店计划/实际观测覆盖、最长缺口、无人处理时段及所有需人工步骤 |
| 72小时 | 断网、正常进程重启与可恢复故障 | 本地缓存/上传确认、任务游标对账、故障前后数据和清理记录；故障测试与自然故障分开 |
| 7–14天 | 重复稳定性及不同日型的数据积累 | 逐店/逐日质量报告、登录/设备依赖、源变化证据；按实际覆盖检查工作日/周末/节假日，未覆盖的类别不算通过 |

服务质量指标至少包括营业时段实际观测覆盖、最长请求缺口、凭证更新成功次数/尝试次数与耗时、需要本人协助的次数、待上传积压、字段缺失和请求失败分类。HTTP成功率不等于上游新鲜度；保护停止也不冒充上游失败。达标阈值应在前两阶段有数据后确定并写入验收报告，不能用这一次恢复计算稳定性概率。

## 历史数据如何进入预测

连续采集解决“以后有历史”的问题，不能立即生成过去几个月的真实记录。三店都需要跨日期、时段和营业状态积累；月份/季节趋势要随实际覆盖扩展，缺少的假日类型单独标为不足。

同时补充可追溯的真实取号、叫号、到店或入座结果，用于两种时间预测及区间校准。有限展示号码变化只提供观测特征，不能识别全体弃号人数；真实过号率和误差仍需相应标签。当前verified_training_labels=0，尚无已验收预测模型。细则见[DATASET_DESIGN.md](DATASET_DESIGN.md)、[OUTCOMES.md](OUTCOMES.md)和[SIGNALS.md](SIGNALS.md)。大语言模型用于有来源的公共外部信息整理/解释与可评估的辅助特征，不负责凭证更新，不收到私有登录或个人结果资料。

## 完全独立服务器路线

最终可考虑向运营方沟通正式第三方数据接入及允许频率，或继续验证有明确授权的正常运行时上下文提供方式。**当前没有已验证的纯服务器正常更新方案，也没有确认运营方提供此类合作接口。** 正式接入是后续沟通方向，不能描述为现成可调用产品。

近期先让正常客户端辅助路线稳定积累数据，同时保持采集器与凭证提供方隔离，方便以后替换来源。只有重复/长期恢复、营业字段与允许频率等验收完成后，才推进更大覆盖和生产服务；采集通过也不等于预测、自动排队或v1.0全部完成。
