# 同店共享刷新需求

rc11新增本机离线 `monitor-stores`，把最多128个用餐计划、最多3个门店合并成每店一份请求目标。它复用[用餐时间策略](MONITORING_TARGETS.md)，不启动持续调度，不查询门店、不读取凭证、不预测叫号或发通知。现有collect仍按固定有界周期运行。

```sh
sushiwait monitor-stores \
  --plans-file /absolute/private/plans.json \
  --as-of 2026-10-06T18:40:00+08:00 \
  --base-interval 300
```

显式输入文件使用schema_version=1、plans数组和可选last_poll_started_at对象。计划仅允许store_id、desired_arrival_at，以及[原时间策略](MONITORING_TARGETS.md)的偏移、状态、外部最早估计和展示集合加速输入；不接受姓名、票号、登录资料或任意网址。无默认路径或环境回填。文件按既有POSIX私有读取器检查本人所有、目录0700/0500、文件0600/0400、单硬链接、无祖先符号链接、16KiB上限与读前后身份，严格JSON拒绝重复键/非有限数。缺失、权限或解析失败只输出固定错误码，不输出路径或原文。

每店在仍等待的计划中取最短请求周期，已明确结束的计划不再贡献需求；相同计划可以属于不同用户，仍合并为一份请求目标。没有等待计划的门店没有下一查询。结果保持确定的门店顺序，只输出聚合数量、周期、下一目标和重算时刻，不输出个人计划列表或理想到店字段。

last_poll_started_at必须由调用方提供该门店实际请求的开始时刻，明确带时区、不能晚于as-of，也不能属于未出现在计划中的门店。工具本身不认证该输入，不能把它当源更新时间。下一请求目标锚定“上次开始+当前周期”，避免每次评估都把目标重新往后推；没有历史开始或已经超时，只要求从当下查询一份，catch_up_requests=0，不补发积压。

计划进入30分钟/15分钟窗口时可能要求加快。后台重算目标取下一查询与未来窗口边界的较早值，避免300秒背景等待错过窗口；重算与查询是不同动作。例如18:28评估19:00计划、上次请求18:28，原下一请求18:33，但18:30先重算。到边界后重新用当前周期判断；输出的时间不会替调度器执行任何操作。加速输入直接要求30秒，不算真实过号率；外部最早估计仍未认证。

**输出仍须按私人计划资料处理。** 即使没有个人明细，聚合数量和边界时间也可能让人推测用餐安排，output_requires_private_handling=true。不能直接上传公开看板、传大模型或声称匿名化。输出保留scheduler_applied/polling_performed/network_performed/notification_sent/business_operation_performed=false、credentials_accessed=false、eta_available=false、true_no_show_rate=null与source_freshness=unknown。周期和due仅是请求需求，不证明允许额度、上游新鲜度或防过号保证；真正执行前还须凭证、互斥、允许频率和失败状态检查。
