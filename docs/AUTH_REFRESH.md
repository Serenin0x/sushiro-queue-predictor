# 查询凭证更新：证据与实现条件

研究日期：2026-10-03，Asia/Shanghai。完整需求与编辑历史见 [PROJECT_HANDOVER.md](PROJECT_HANDOVER.md)，实际命令见 [DATA_ACCESS.md](DATA_ACCESS.md)。本文记录已观察到的正常流程及进入自动更新实现前还缺什么，不提供寿司郎官方接口合约。

## 已经验证的链路

本人正常启动的同域会话出现以下顺序：旧授权查询401 → POST `/api/1.3/initialize` 返回200及新 `data.auth_token` → 后续门店查询使用该新授权。响应凭证与后续请求在本机精确匹配；从成功详情导入完整上下文 revision 2 后，电脑再次读取三店成功。观察本身没有重放初始化请求，也不证明401的唯一原因。

门店查询凭证、初始化登录码与其他命名凭证分开：

| 对象 | 已知事实 | 能否直接作为自动更新方案 |
| --- | --- | --- |
| 门店查询 authorization | 新样本未验签声明20:32:49–21:32:49；20:41三店查询成功 | 可在本机保护范围内查询，不能因此取得下一份凭证 |
| 初始化 long_token | 本次非空、opaque；无可读取iat/exp声明，与四份已交付HAR中的查询授权均不相等 | 来源、用途、期限、轮换和单独更新能力未知；名称不证明长效 |
| 初始化 js_code | 本次非空字符串 | 正常生成来源与服务端校验未知，不保存旧值作未来更新 |
| 初始化 sign / nonce / ts | sign为64个十六进制字符，nonce为字符串，ts为整数且与捕获秒级时间相符 | 签名算法、输入、密钥/正常生成方式和时间容差未知；形状不能证明SHA或HMAC |
| device_id / app_version | 本次为字符串 | 正常来源、绑定关系和必需性未知 |
| gateway initialize 返回的另一 auth_token | 与实际查询Bearer不同，expires_in=86400，expiry与捕获时间加该期限相符 | 未核验用途与权限，不替换查询授权，不宣称门店查询凭证有效24小时 |

上述字段在一个成功请求中出现，不证明每个都必需，也不证明服务器提供或不提供其他正常更新方式。没有省略字段、猜签名或用其他凭证试探查询。

## 微信登录码的资料范围

腾讯官方 [api-typings 固定提交中的 LoginSuccessCallbackResult](https://github.com/wechat-miniprogram/api-typings/blob/6092df9100c73b84e140c20b9a42a8e8799e0660/types/wx/lib.wx.api.d.ts#L7861)说明，wx.login 返回的 code 有效期为5分钟，开发者服务端用它完成登录兑换。仅凭HAR中的字段名，还不能确认寿司郎两个不同的 js_code/jsCode 正是该返回值；这个对应是待验证推断。本文没有用官方类型文档推断寿司郎签名协议，也没有核验登录码一次性使用规则。

本轮公开搜索包括实际SAPI主机与initialize、sushiro与long_token，以及参考仓库中的long_token/js_code；GitHub两次代码搜索均返回0条，网页检索未获得可核验的寿司郎参数生成协议。搜索范围有限，不能据此宣称协议不存在或独立更新永远不可行。腾讯OneID是另一产品，TCSAS是另一宿主体系，不将这些产品的登录方案直接当作寿司郎协议。

## 可执行的状态检查

dev4新增以下零网络检查，不需要把私有上下文放进环境变量：

```sh
PYTHONPATH=src python3 -m sushiwait auth-status --api-profile miniapp_gateway --credentials-file "$SUSHIWAIT_CONTEXT_FILE"
```

整组文件沿用当前安全读入、profile/schema/权限限制，不与环境拼接。输出只含安全声明时间、revision、checked_at和本机保护状态，不含文件路径、请求头、账号字段或凭证值。文件验证后才读取当前时间，不修改文件或数据库。

| authorization_guard.state | 含义 | 后续采集的处理 |
| --- | --- | --- |
| no_declared_stop | 声明可解释且当前没有触发30秒保护 | 仍需正常只读请求验证当前接受；这不是服务端有效性结论 |
| stop | 声明过期、临近到期或时间顺序无效；stop_reason区分原因 | 不发查询；取得完整正常新上下文后重新检查 |
| unknown | 声明不可解释或缺到期时间 | 不推默认TTL，不等于已到期或无限有效；当前查询逻辑仍按既有规则处理未知声明 |

exit0 / ok=true表示检查完成，**stop或unknown也会exit0**。文件缺失、损坏、权限不安全或profile不符为固定安全错误/exit1，不回退环境。每次命令是独立检查，不保存跨进程revision历史，也不证明更新后的服务端接受。省略文件参数时原环境模式及原输出保持。

该功能没有实现定时器、告警送达或自动更新；后续后台必须读取保护状态，不能仅凭退出码决定是否发查询。

## 自动更新的进入条件

实现前先取得并记录下面的实际证据，按最先可验证的路线推进：

1. 确认SAPI提供的正常更新契约：是否支持直接更新、需要哪些字段、正常错误分类及凭证轮换规则。仅long_token是否足够目前未知。
2. 若依赖微信登录码，核验其真实生成来源、应用身份关系和可用运行环境；普通服务器发HTTP请求不能仅凭一份HAR生成新的运行时登录码。这是当前缺少生成步骤的判断，不是“所有续期必须开微信”的既定结论。
3. 核实签名输入、设备绑定与正式生成方法，使用正常支持的协议；不从一个摘要反推算法或把样本签名当永久配置。
4. 将整组新查询上下文写入既有私有文件，递增revision、当下检查30秒保护并原子提交；初始化其他凭证不能混入查询整组。
5. 首次接入真实更新提供方后，再验证服务器接受、运行中整组切换、连续跨到期、失败停止与恢复。当前文件替换离线回归和新进程查询成功不能替代这一步。

目前可用的是显式人工更新边界：正常流程取得新上下文 → 离线检查 → 显式导入 → 重新核验。只作为开发试点手段，不当作服务器全天方案，也不要求用户为日常采集不断刷新手机。官方接入或受支持的更新提供方尚未落实；依赖微信运行环境的辅助端仍只是备选，需要单独核实能力和运行范围。

初始化POST尚未加入客户端；没有假续期函数、无依据自动重试、常开解密、跨域转发、购买接入或联系第三方。当前下一步是补正常参数生成证据及可行路线；字段现场核对、电脑有界门店验证和采集故障处理可继续独立推进。
