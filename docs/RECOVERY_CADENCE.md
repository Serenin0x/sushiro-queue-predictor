# 凭证恢复后的采样目标

rc16让单店保留原采样目标。rc22进一步减少普通`collect`和持久有界任务的多店恢复等待：完整一轮结束后，保留已安排的下一轮目标，并至少等待到**上一轮最后一次观测完成后的一个周期**。这个保守边界覆盖各店上次查询开始时刻，避免串行响应变快时提前查询；已过目标就从当前查询一次，不补发积压。正常采样、声明到期前30秒保护、新授权/更高revision要求和首错停止保持。

rc24仅在显式开启[有限5xx额度](TRANSIENT_SAMPLING.md)且本轮发生符合条件的错误时，把下一轮目标再限制到最后观测完成+interval；失败槽位不重试，默认0额度保持原首错停止，401与正常凭证恢复规则保持。

如果原目标还没到，就继续等到原目标；如果已经错过，只查询一次当前状态，随后从新一轮开始时间按正常周期运行。不会补发暂停期间欠下的查询，也不会因为更新提前成功而抢在原目标之前请求。

以下均是合成时钟验证，秒数相对于测试启动，不能当真实接口成绩：

| 场景 | 原采样目标 | 新上下文接受时刻 | 实际模拟采样 |
| --- | --- | --- | --- |
| 单店提前恢复 | 30秒 | 6秒 | 0、30、60秒 |
| 单店较晚恢复 | 30秒 | 45秒 | 0、45、75秒 |
| 多店提前恢复，响应无模拟耗时 | 一轮30秒 | 6秒 | 各店0、30秒；不额外等到36秒 |
| 多店较晚恢复，响应无模拟耗时 | 一轮30秒 | 45秒 | 各店0、45、75秒；不补发30秒的旧槽位 |
| 两店串行响应10/9秒 | 一轮30秒，上一轮19秒完成 | 33秒 | 第一轮0/10秒，下一轮49/59秒；保留19+30秒安全边界 |

普通`collect`和私有有界任务都检查提前、延后、串行耗时和新凭证在等待期间再次进入保护。若凭证恰在目标时刻进入保护，恢复发生在下一轮首次GET预检，也应用同一个完成边界并在使用时重读配置。不会再启动第二个等待预算。轮内尚未查询完所有店时的原恢复策略保持；这项变化不是常规每店独立调度。

任务退出后显式`--resume-task`没有可靠的同进程单调完成时刻，仍先等待完整周期。合成部分轮次重启/期间更新案例中，第一店0秒结果只保存一次，重启后第二店36秒、下一轮66秒，保持对账与保守等待。HTTP401或504仍不自动等待/重试。

两种模式仍每次GET前重读整组上下文，坏文件、回退/同版本冲突、同授权或临近失效的新上下文都不能通过。恢复后等原目标期间再次预检失败，会停止，不重开一个无限等待预算。首次启动就遇到过期时，没有旧的采样目标，沿用现有通过新上下文后查询的流程。

这项修改只减少程序额外等待，不缩短正常客户端产生新授权、短窗接入、关闭回读、名单恢复与主配置提交本身的时间。到期前30秒保护可能先于新授权实际产生，因此不承诺无缝更新或30秒防过号覆盖。真实恢复缺口、运行包与过程单独记在[交接文档](PROJECT_HANDOVER.md)，完整来源和人工边界见[长期采集方案](LONG_TERM_COLLECTION.md)。

`monitor-collect`仍是独立的有界自适应入口，当前遇到凭证保护直接停采，不使用此恢复流程。不会用固定周期单店的结果替代自适应采集的验收。

已安装最终rc16已完成一次真实同进程11→12恢复：西单6成功、另1本机到期保护，跨更新查询开始间隔98.760秒，恢复后29.988–30.007秒，见交接E0155。全部闭店/源新鲜度未知；该结果不代表连续30秒覆盖或完整自动更新控制器。

rc22新增7个场景，两个恢复/任务模块50项0.618秒、完整704项10.271秒OK。初次专项发现持久任务在精确保护边界会从首次GET预检恢复，修正后同时覆盖两条路径；当时仍在运行的90轮任务使用rc20初包，不把代码修改套到该进程的179秒缺口上。

后续已安装rc22营业三店30秒任务完成90份成功/另1次到期保护，正常14→15恢复缺口102.241–102.280秒，见E0194。午间另一原rc23三店60秒任务中，正常15→16的143.118–143.122秒、16→17的127.124–127.161秒分别见E0202/E0210。17这轮清理批次实际一次编辑确认原名单后退出小程序，原进程恢复；缺口减少仍不代表30秒连续监控或常驻无人值守验收。各独立库、运行包和周期分开，不能把更新后的代码、历史30秒结果或软件检查套到别的运行。
