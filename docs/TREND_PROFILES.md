# 相似日期的展示变化参考

rc51新增原创历史参考组件：将当前堂食／预约展示号码的集合周转，与同店、相似日期的已保存窗口比较。它提供可解释的相对快慢数字，连接[自动已有号追踪](TICKET_TRACKING_LOOP.md)及[公共AI契约](DISTRIBUTION_FUSION.md)。展示消失不等于已叫号、入座或弃号；本模块不估真实过号率，也不把变化率直接换算成等待分钟。认证真实结果仍为0，`eta_available=false`。

## 历史怎样成为参考

只读取操作者明确指定的已结束、闲置门店数据库，不复制或打开正在采集的活库。沿用完整历史校验、32MiB／10,000条上限、独立响应时刻、失败与跨运行边界；有并发写者、损坏记录、超限或读前后状态变化则拒绝整次操作。不会以最近若干行悄悄代替完整资料。

按UTC整点网格划分不重叠的完整窗口，默认30分钟；可选120–3600秒。最多96个候选窗口，超出时拒绝，不静默截断。参考保存窗口结束时刻、可比较次数、实际覆盖毫秒，以及堂食／预约各自展示消失数。默认至少2次比较、覆盖半个窗口；允许的响应缺口默认360秒。两端都须符合窗口与资料可用条件，失败、重启、逆序或长缺口断开；原始数量查询失败不把有效展示变化补成零或抹去。

有两种明确的信息可用依据：

- `local_first_receipt` 为默认严格模式。采用每个历史时刻当时已记录的[本机首次接收](ANONYMOUS_INTAKE.md)资料；后来接收的旧响应不提前进入窗口。旧记录缺少接收资料时不填造时间，可能得不到参考。
- `sealed_response_reconstruction` 为显式封存重建。操作者现已持有完整闲置数据库，按其中响应时刻重建过去的展示窗口，参考最早只从**现在创建以后**用于前瞻比较。它不证明这些资料在过去某预测时刻已收到，不能用于声称无泄漏的历史回测。不会向原库补写首次接收时间。

两种模式都保留`historical_availability_verified=false`：本机时刻记录和文件哈希不是外部认证。创建时刻、历史截止、来源依据、规则和全部样本纳入规范内容哈希；新文件权限0600、目录0700、上限16KiB，已有文件不覆盖。

## 当前速度怎样比较

当前摘要必须来自正在运行写者的提交，响应未过时、输入未到期、窗口有足够实际覆盖与比较。保存的旧历史、停采、长缺口、资料不足均返回未知；读取时钟不伪装成上游刚更新。堂食与预约分别使用自己的消失数，实际可比较毫秒作分母；不使用号码差、等待桌数假设或整个窗口长度充当有效覆盖。

历史窗口须结束在当前窗口开始之前，避免参考与当前重复。采样间隔也影响有限展示集合的饱和程度：参考的平均可比间隔须处于当前的0.8–1.25倍，不能把5分钟采样和30秒采样直接比较后声称突然快过号。此范围是明确的研究规则，未由真实等待结果校准。

日期使用当次预测时已知的日历公告。由细到粗尝试：

1. 日型、周几、小时、月份。
2. 日型、周几、小时、季节。
3. 日型、小时、季节。
4. 日型、小时。
5. 日型。

所有层都保留相同节假日名称，春节样本不会成为国庆参考；未知日历覆盖不视作已知日型。默认至少8个合格窗口、2个不同当地日期，单日多窗口不能替代多日资料。输出实际命中的层级、窗口数和日期数。当前不跨门店／城市借资料，小时取窗口结束时刻，午夜与营业日边界仍需后续业务核对。

对当前速率`r`，输出两个经验位置：严格小于`r`的参考比例向下取整，以及小于或等于`r`的比例向上取整，均用百万分之一整数保存。同值保留区间；全部为零或全部同值会得到`[0,1000000]`，不误报100%异常。下端达到90%记较参考快，上端不超过10%记较参考慢，其余为常态或同值。它是描述性排序，参考窗口仍有时间依赖；**不是异常概率、叫号风险、置信区间或已校准等待分布**。

## 算法与AI怎样使用

公共特征新增实际覆盖毫秒，以及所选队列的排序下端／上端、参考窗口数／日期数。四个排序字段成组校验，资料不足全部为null；不把缺失参考数0传作确定低速。窗口文件路径、哈希、样本数组和个人号码不进入大模型输入。

自动追踪可重复给`--trend-profile-file`，最多3家、每店一份；文件须与私人会话目录分离，来源门店／格式／创建时间在工作线程启动前检查。追踪根据参考的窗口长度整理写者已有投影，再注入数值特征。文件启动时读取一次，不热更新；新版本仍须遵守[私人提交检查](MANUAL_TICKET_TRACKING.md)。它不新增上游请求、不改变采集预算／期限，不阻塞采集工作者。

当前CLI历史候选仍只有一个情景，所以不会为了这些新特征产生无作用的付费调用。库调用方提供真实拟合的多情景以后，受限公共建议才可能改变融合权重；供应商授权、钥匙、预算与当前版本检查继续按[DeepSeek规则](DEEPSEEK_ADAPTER.md)执行。历史初估、实时等待情景训练、真实叫号结果和同期有／无AI比较仍需完成。

## 本机研究步骤

下例900001为合成店号，时间和文件均为示意，不可拿它查询真实门店。先确认采集已自然结束、数据库没有写者，再为每家真实店分别建立新参考文件。

```sh
sushiwait trend-profile --remote-db sealed/remote.sqlite3 --store-id 900001 \
  --as-of 2026-10-07T14:00:00Z --output reference/store.json

sushiwait trend-score --profile-file reference/store.json \
  --context-file current/context.json --output research/score.json
```

旧库缺少首次接收资料时，只有显式追加`--availability-basis sealed_response_reconstruction`才允许前瞻重建；保持默认严格模式得到0窗口也属于正确的资料不足结果。`trend-score`读取新鲜、严格格式的公共上下文，保存`public_context`与私人`trend_score`，标准输出只给是否保存、趋势可用及参考数量，不打印路径或展示号码。旧输出不覆盖；提交与持久化确认分开。

之后显式启动的新追踪任务可在既有参数上追加：

```sh
sushiwait ticket-track-run --state-dir personal/state --store-id 900001 \
  --collector-url http://127.0.0.1:8765 --duration 3600 --max-cycles 720 \
  --trend-profile-file reference/store.json
```

正在运行的rc43／rc45六店真实采集保持原300秒周期、期限、预算和版本；它们不会因为源码升级自动取得新追踪路由，也不为此重启或外读活库。统计页继续显示写者投影，当前没有在产品页面展示此研究排序。

## 实际资料与验证边界

已自然完成的三店24小时测试保存672组成对观测、每店224组。数据库确实没有首次接收元数据：默认严格模式各0窗口；显式前瞻封存重建各33个合格30分钟窗口，原文件哈希未变。旧投影不能用作当前实时输入。这批资料只有很短的日期跨度，不能宣称已学习各种月份、季节和工作日；原长缺口记录保留，不以成功总数认证全天连续。

30项专项和完整1401项软件检查通过，涵盖当前／参考时刻、采样间隔、同值、不同日期、损坏／并发数据库、私有CLI及真实追踪线程。安装包和Linux验证、公开提交与精确CI分别记录于[交接文档](PROJECT_HANDOVER.md)，不将合成判断说成真实预测效果。

## 研究依据与后续

当前经验排序是本项目原创可解释基线。研究参考了[多季节实时异常检测](https://arxiv.org/abs/1908.01146)、[非交换数据的split conformal](https://jmlr.org/papers/v25/23-1553.html)及[在线分布变化下的conformal](https://jmlr.org/beta/papers/v25/22-1218.html)的官方摘要：分别涉及季节变化、原交换性前提的限制、在线调整。此处只读出处与摘要，没有复现论文算法，没有实现其LTI或conformal，也没有搬用其精度或理论覆盖保证。

本项目据此选择先区分日期、真实覆盖、采样节奏及资料不足，后续再按整组号单的时间顺序验收等待情景和误差。经验排序不能单独证明季节模式或弃号原因；必须继续收集跨日型资料、真实叫号结果，检查有限显示饱和、号码周期和模型延迟，再决定是否引入在线变点及校准方法。
