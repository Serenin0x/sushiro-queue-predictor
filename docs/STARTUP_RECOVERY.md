# 扩店首次建档故障与有限恢复

2026-10-10 10:30自动开采后，147店中的103店开始保存观测，44店在首次建档报`daily_controller_storage_or_input_error`。实际进程软文件上限1024／硬上限524288，103个正常工作者下已占833个描述符。每店同时持有控制器、campaign、任务、数据库描述符；此前未来任务／内存容量检查未覆盖147店同时打开真实日数据库的文件上限。

准备工具现在对共享采集服务显式生成`LimitNOFILE=8192`；不修改来源请求速率、营业时间、内存限制、权限或网络端口。已运行服务器需要安装该服务的同值drop-in并正常重启；仅修改准备工具不会改变运行实例。

[恢复工具](../deploy/repair_daily_startup.py)仅用于这类**未发布首个窗口且零查询**的首次建档事故。先停止共享采集服务，取得fleet、各控制器／campaign／任务排他锁；逐店验证当前日未到原截止、campaign active且windows为空、控制器因存储／输入错误halted。孤立window-01只能有空锁、初始task、空SQLite或空remote_samples表；pending、尝试次数、任何观测、未知文件／目录、错误权限、过期和已有发布窗口全部拒绝。所有门店先验证再修改。

工具将原controller／campaign字节、SHA256及孤立初始窗口保留在采集根以外的0600／0700事故目录；控制器只恢复active、清除已确认的启动错误并更新时间，原日配置、创建时间、截止和预算保持。不删除旧记录、不把漏采时间补为成功、不追赶发请求。恢复后的首次新查询受现有来源门控和营业时段限制。

默认仅验证；明确`--apply`才写入。恢复前应确认共享服务已停止，正常门店以原检查点恢复，不开第二个同店写者。该工具不是一般故障重试，不能恢复限流／授权失败、有pending或实际尝试的任务。实际云应用与恢复结果另记项目交接编辑历史。

实际首次停止后只有40个持久化halted标记；另4个失败工作者仍是active／null，因为文件耗尽也影响错误落盘。工具允许这两种控制器状态，但同样必须验证未发布窗口、无pending、无尝试和空数据库；不能仅靠active状态授权恢复。44家按实际空窗口证据识别，不能只筛halted或通过硬编码数量修改无关检查点。
