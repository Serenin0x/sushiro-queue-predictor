# 后台取号与批量验证

2026-10-14，E0510。用户希望减少人工配合，研究后台自动取号，并用大量样本自动验证。结论：**后台提交本人取号有可研究的实现线索，但本项目尚未验证写入闭环；大量不就餐的真实取号不适合作为等待模型的训练方法。** 本轮真实取号、取消、签到、个人号单查询均为零，未更改生产采集或重新读取官方代码包。

## 为什么大量取号不能自动得到大量真实等待标签

用户10月10日提供的官方页面截图写明，到店后需要签到，否则不会叫号，未签到也可能进入过号处理。因此一个后台取出却没有真实到店的号，和正常就餐者经历不同。显示号码越过目标，只能支持号码参考位置的观察，不能证明该号实际被叫。

重复取号、取消还会改变发号序列，可能影响门店或其他顾客，并让模型学到我们自己制造的退出行为。若日后做少量业务验证，需把这些测试号标记为probe，和自然用餐数据分开；不得混入真实弃号率或正常等待训练。取消也不是实际叫号的替代结果。

## 建议分成三条自动验证流程

1. **公共记录回放**：从当前时刻的号码参考值选固定偏移目标，例如+20/+50/+100；以后只读观测检验推进。可批量运行，完全不生成真实号。本轮已经实现，见[低频回放](SPARSE_DISPLAY_REPLAY.md)。它检验趋势算法、信息不足和采样误差，不认证用户等待准确率。
2. **隔离业务模拟**：用本地替身或官方提供的测试环境验证提交超时、重复点击、重启、取消失败、手机同时换号等流程。大量取号只在这类不占真实排队资源的环境进行。当前未取得官方测试环境；不能把本地模拟成功写成官方接口已通。
3. **少量真实就餐闭环**：针对本人正常用餐，先确认已有号，再取一次，自动查询并记录取号／签到／首次有效叫号的来源与时间。用户或现场只补接口无法证明的真实结果。获取支持这些事件的本人号单接口后，可减少手工抄录；不能假装现在已经有这个接口。

## 后台写入流程应怎样实现

将自动取号从公共采集服务独立出来，公开统计页不暴露写入入口。每个账号同时只处理一个业务意图；持久保存操作ID、门店、日期、人数、桌型和凭证版本，在发出请求前先记账。

状态顺序为：`prepared → checking_existing → submitting → confirmed / rejected / unknown`。已有有效号时不覆盖；超时或连接中断进入unknown，通过本人号单查询核对是否已成功，不盲重发。只有上游确实支持幂等键才依赖它；本机锁不能保证上游恰好执行一次，也管不到用户手机上的并发操作。

取消应走独立状态：核对号码身份和当前状态，提交一次，再回查。取消未确认前不重取；发现手机换号或结果不一致就停止该意图。若上游只能“取消账号当前号”，需明确核对与取消之间仍存在竞态，不能承诺百分之百不会取消错号。采集凭证更新可以独立继续，不能在恢复后自动重放未确认的写操作。

真实业务核对时，应保存HTTP状态与业务状态、请求开始／接收时间、服务端创建时间（若有）、号单ID、队列／桌型、原号、结果来源和审核状态。私有信息不进公共统计、GitHub或LLM。没有服务端创建时刻只记录提交区间；精确逐号发放仍是[后置研究](TICKET_ISSUANCE_RESEARCH.md)。

## 先做什么

当前继续官方三店有限稳定性试验，同时使用保存数据开发预测。后台取号先完成接口证据和状态流程设计，不将批量真实出票设为预测的前提。未来需要核对一次正常本人取号和查询号单响应；若现有授权资料没有这些内容，就等真实用餐机会补齐，不猜测写接口或扩展抓取范围。自动取号／取消／重排仍保持核心1.0之后的路线，除非用户明确调整发布范围。
