# 前端设计板块

本板块供负责产品设计的 GPT、设计师和前端开发者接手。它规定页面应有什么、数据怎样解释、用户怎样操作；具体视觉由设计聊天推进。最新R48／R49要求浅深色、简洁留白及少边框，替代此前只做浅色的视觉约束；参考选择见[视觉记录](VISUAL_REFERENCES.md)，事实阶段仍看完整交接。GitHub 品牌资产和产品界面分别维护。

## 从这里开始

1. 阅读本页，了解产品流程与实现阶段。
2. 阅读[页面内容规范](CONTENT_SPEC.md)，据此整理页面清单、状态和文案。
   接真实统计数据时阅读[接口、字段与发布接入说明](STATISTICS_INTEGRATION.md)，沿用现有采集后台。
   可以直接导入[无框架统计接入包](integration/README.md)，复用请求、选择竞态、轮询、月历和曲线转换；当前还未部署到线上视觉页面。
3. 阅读[项目完整交接](../PROJECT_HANDOVER.md)的最新记录和要求；那里是需求与发布事实的主要来源。
4. 实现页面前核对实际代码／接口，使用下方文件入口；设计稿不得把计划功能写成已经上线。

## 产品与用户任务

展示名为 **SUSHIWAIT**，仓库名保持 `sushiro-queue-predictor`。服务面向中国大陆寿司郎门店，帮助用户看到叫号变化、估计自己的等待、安排到店时间，并在突然加速时及时调整。项目为独立开源软件，产品文案不表示寿司郎官方运营或授权。

用户的主要任务按此顺序组织内容：

1. 找到想去的门店，查看最新堂食／预约展示号和数据更新时间。
2. 已在官方客户端取号的用户输入自己的号码，查看随新观测更新的预测及误差状态。
3. 尚未取号的用户按理想用餐时间和等待偏好，查看建议取号时机；这是后续两种预测中的反向模式。
4. 查看月历和单店当天曲线，了解不同时段的号码变化。
5. 临近用餐查看提前叫号风险，并记录正常用餐的实际时间，帮助校准模型。

自动取号、取消和重排保留为后续阶段。精确逐号发放时刻只做研究，不在 v1.0 部署。设计这些后续内容时应明确阶段，当前界面不显示看似可用的执行按钮。

## 建议的页面划分

页面名称是内容分工，设计者可调整导航与布局，但不得遗漏所列任务。

| 页面／区域 | 核心问题 | 必需内容 | 当前阶段 |
| --- | --- | --- | --- |
| 门店选择 | 去哪家？这家有数据吗？ | 名称、可用地区资料、搜索、采集／预测可用状态、最近响应时间 | 已有门店筛选，可完善 |
| 门店实时信息 | 当前列表是什么？数据多旧？ | 堂食及预约各前三位、原顺序、更新时间、失败／闭店／未知状态 | 数据展示基础已有 |
| 我的号码 | 我大约还要等多久？ | 门店／队列／本人号码、已知取号时间、当前结果、误差状态、调整依据 | 参考实验已有；可靠等待预测待接 |
| 计划用餐 | 我什么时候取号合适？ | 理想到店时间、正负偏移解释、建议取号时间及区间、资料不足原因 | 后续核心v1功能 |
| 每日统计 | 某天某家店发生了什么？ | 月历、当天总览、单店曲线、原前三位明细、覆盖与缺口 | 已有，可完善 |
| 提醒／追踪状态 | 是否需要提前到场？ | 预测提前、突发加速、数据失效、提醒权限／送达状态 | 后续核心v1功能 |
| 用餐经历 | 实际什么时候取号和叫号？ | 本人已知事件时间、未知／大约范围、修订与结束声明 | 页面内草稿已有，云端私人提交待接 |
| 服务说明 | 这些结果依据什么？ | 当前能力、更新时间、数据与个人信息使用说明、开源入口 | 与上线能力同步维护 |

## 设计任务的交付内容

每一页面应交付：信息顺序、字段及说明、输入与操作流程、加载／空数据／失败／闭店／过期／资料不足状态，以及手机和桌面上怎样完整表达内容。当前先交这些内容，视觉方案另行处理。

对新增功能写明：已有接口还是待接入、依赖哪个模型结果、哪些操作仅在本地发生、哪些以后需要私人服务。设计稿中的数值样例标明合成，不作为真实统计或上线能力证明。

每次实质设计变更同步本板块和[完整交接历史](../PROJECT_HANDOVER.md)，记录改了什么、原因、对应要求、实现阶段及下一步。不擅改正式Logo、README已认可视觉或采集／预测业务语义；正常内容调整在已授权范围内继续，不为日常编辑重复索要确认。
