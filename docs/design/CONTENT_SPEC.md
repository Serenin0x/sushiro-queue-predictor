# 前端页面内容规范 · DS-001

本文是[前端设计板块](README.md)的内容契约。字段、状态和文案必须跟随实际实现更新；数据逻辑以代码和[完整需求](../PROJECT_HANDOVER.md)为准。用户界面使用普通人能懂的语言，接口字段名、模型策略名、凭证和调试信息留在开发文档。

## 统一的时间与数据规则

- 日期、营业日和时间展示统一北京时间，时间格式要让手机用户看得清。数据内部UTC转换到界面，不把UTC日期直接当店铺日期。
- “最近响应”指服务器收到查询结果的时间。“页面更新”指浏览器读取副本的时间，两者分开；页面刷新不表示上游刚更新。
- 保留原号码字符串及顺序，含前导零／前后缀；显示原前三位，不排序、不用最大号码当当前游标。
- 用户约定第一位作当前叫号参考，界面标题可用“当前叫号参考”，附近简短说明“显示的是即将叫号列表，实际状态请以官方号单为准”。不要让每一处文案都充满技术说明。
- 堂食对应mixedQueue，预约对应reservationQueue。storeQueue是可能包含预约的汇总，不用它替代堂食预测；吧台／卡座暂作为展示，预测是否支持须按模型实际能力。
- 没有观测、观测失败、字段未显示、统计加载中、确实有效的零值分别表达，不用0或“无人排队”替代未知。
- 初期营业时间为用户假定：自然周一至周五11:00–22:00，周末／已知节假日10:30–22:00；单店覆盖优先。页面称“当前采用的营业时间”，不能伪称官方核验。
- 资料陈旧、失败或门店／队列切换后，旧预测撤回或明确失效；迟到请求、旧AI输出不能覆盖新选择。

## A．门店选择和实时信息

门店入口至少提供名称搜索、店铺选择、当前有无观测和最近响应时间。地区、地址和营业时间仅在资料真实可得时显示，不从店名猜地址。可浏览目录与当前已采集／可预测门店分别标记；147个已知店号不宣传为今日全国所有门店已经稳定覆盖。

选定门店后，优先显示堂食和预约各前三位；多个号码逐个呈现，不压成“当前叫到最大号”。原始数量单位目前未知，使用“原始数量（单位待核）”，不直接标为“已签到等待桌数”。只有核对过单位的字段以后才能换标题。

| 状态 | 应表达的内容 | 操作 |
| --- | --- | --- |
| 首次加载 | 正在读取这家店的数据 | 可以换店；不显示上家店号码 |
| 已有有效响应 | 原前三位、最近响应时间、队列名称 | 查看曲线／输入本人号码 |
| 列表为空 | 本次列表未显示号码 | 保留响应时间，不说无需等待 |
| 闭店等待 | 当前采用的营业时段、下一次开始时间（若可确定） | 仍可查看历史 |
| 响应较旧／采集停止 | 最近成功时间、当前未获得新观测 | 旧预测暂停，可手动刷新副本 |
| 单接口失败 | 可用部分保留，失败部分写未知 | 不把整页所有字段清零 |
| 读取失败 | 当前数据暂不可用 | 重试读取，不自动取号或重启采集 |
| 门店尚未采集 | 此店暂没有已保存观测 | 保留目录状态，不能显示模拟数字 |

## B．已有号码与实时预测

核心流程：选择门店及堂食／预约 → 输入自己的号码和已知资料 → 确认号码属于当前门店及队列 → 显示可用预测 → 随新观测更新。用户先在官方客户端正常取号，本项目不把输入号码等同于取得官方排队资格。

| 输入 | 内容规则 | 当前实现与后续 |
| --- | --- | --- |
| 本人号码 | 字符串，保留原格式；不同门店／队列不混用 | 当前浏览器参考算法只支持1–7位纯数字；后台支持范围更宽不表示浏览器已支持 |
| 取号时间 | 用户已知的实际时间；未知可保留未知，不默认填当前时间 | 当前参考实验要求今天的已知取号时间；未来私有模型允许未知输入并明确哪些计算不可用 |
| 门店／队列确认 | 用户显式确认；换店、换日期或换队列重新确认 | 当前实验已实现 |
| 人数／桌型／签到状态 | 可选且允许未知，只使用模型实际支持的字段 | 私有后台有字段，当前公开实验没有完整输入界面，不伪造已签到状态 |
| 理想到店时间 | 可选的私人计划，与实际取号时间分开 | 后续接入监控／提醒；不能只为提频强填时间 |

结果区优先呈现：预计还需多久、预计叫号时段、较早／较晚范围、最近依据时间和变化原因。当前只有未校准参考模型时，使用“参考位置预计到达时间／快慢情景”，不改称已可靠校准的实际叫号。误差未经验证时显示“误差尚未校准”，不能写“±5分钟／90%准确”。

历史初估与实时修正分别说明：刚输入号码先使用截止已知的相似历史；新叫号观测到来后修正。页面不要仅做静态倒计时。可解释的变化原因包括“最近推进变快／变慢”“相似日期资料不足”“新观测暂不可用”；不显示模型内部权重或大段推理过程。

| 预测状态 | 页面内容 | 禁止的误读 |
| --- | --- | --- |
| 输入未完整／未确认 | 缺哪个必需输入，如何补充 | 不替用户确认门店或填取号时间 |
| 历史初估 | 使用了哪些可用历史层级、初估时间及范围 | 不暗示已经看到取号后的现场变化 |
| 已实时修正 | 当前结果、更新时间、相较上次提前／延后、主要原因 | 不把浏览器刷新当新叫号观测 |
| 仅有未校准参考 | 参考时间／情景范围、误差状态 | 不将情景区间称统计保证 |
| 资料不足 | 暂无法估计，已知的门店号码继续显示 | 不显示0分钟或任意全国平均值 |
| 突然加速 | 较早端变化和建议核对官方号单 | 不用展示跳变直接宣布确定过号 |
| 号码已在展示中 | 说明在该次响应看到，建议查看官方号单 | 出现不自动等于实际已叫 |
| 曾出现后消失 | 当前状态待确认、最近观测时间 | 消失不自动等于过号／入座／取消 |
| 参考倒退／轮次未知 | 无法确认号码周期，暂停数值结果 | 不拼接跨周期的速度 |
| 数据过期／失败 | 预测暂停，等待新观测 | 不让旧分钟数继续正常倒计时 |
| 用户结束追踪 | 结束本项目追踪的状态 | 不声称取消了官方排队号 |

当前浏览器仅在90秒内的新观测、至少5分钟有效连续趋势等条件成立时计算；具体边界由reference-model.js返回状态决定，不由设计稿覆盖。后续历史模型接入后同步修改这里的条件，不把实验阈值写成永久业务规则。

## C．理想用餐时间与偏移

页面必须拆开“理想到店／用餐时间”“希望叫号相对这个时间的偏移”和“模型预测误差”，三个概念不能合并为一个“误差”输入框。

定义：目标叫号时间 = 理想到店时间 + 用户偏移。

| 例子 | 正确含义 | 建议文案 |
| --- | --- | --- |
| 理想到店18:00，+10分钟 | 目标18:10叫号，18:00到场后大约等10分钟 | 希望到店后再等10分钟 |
| 理想到店18:00，−10分钟 | 目标17:50叫号，早于理想到店10分钟 | 希望提前10分钟叫号；需安排更早到场 |
| 预测范围17:55–18:20 | 这是模型的不确定范围 | 与上面的偏好单独显示 |

未来结果应显示建议取号时段、预计叫号范围、目标偏移、提前／延后风险及最新依据。没有可用模型或当日放号资料时，不输出假精确的预约时间；建议只供用户在官方客户端执行，不做真实自动取号。

rc68已有[后台完整候选评分](../IDEAL_TIME_PLANNING.md)，当前没有用户界面或云端反推入口。结果选择的是明确网格中的一个未来取号时刻，不是已验证连续取号时段或实际可放号时刻。页面接入后，接受提前／过晚的范围应独立于有符号偏移；显示模型资料不足、偏好无法满足、候选已过时或观测不可用的区别。经验质量界未校准时不能直接宣传成“保证准时概率”。

## D．日历、当天总览和曲线

- 月历按真实月份天数与北京时间日期生成，支持换月份、点日期及筛门店。全部店与单店模式都应保留选择上下文。
- 当日总览显示：有观测门店数、配置门店数／尚未加载门店数、完整观测组、失败与营业边界暂停、覆盖、最近观测。扩店后总数不直接用于跨日人流比较。
- 日历颜色当前只表达采集覆盖。无数据、未加载、低覆盖、有覆盖需可用文字分辨；不只依赖颜色。以后客流配色需有可靠叫号量及稳定比较范围，不先写高峰／低峰。
- 单店第一张曲线横轴时间、纵轴列表第一位号码位置，标题“当前叫号参考—时间”；遇空列表、失败、长缺口、重启／倒退不连成连续稳定速度。
- 其他曲线分别显示原始数量、展示变化速度；单位未知保留说明。有限三个展示号码的消失数量不等于餐厅实际处理桌数或真实过号率。
- 明细保留每次时间点的三个原始号码、队列与状态。当前页面仅返回有界曲线、最近60条表格；“图表有截断”和“原始数据仍保存”分别说明，不能称最近60条就是全天数据。
- 尚未结束的采样格、已完成格、原操作开始覆盖与响应接收覆盖口径不能混写。新日质量报告仍是私有归档工具，没有公开路由时不设计成已经可点击下载。

全月后台校验期间，先显示已完成的数据和加载进度，未加载内容不能变成0。月切换、店切换和日期切换后，旧请求回来不得覆盖新选择。现有statistics.js已有这些保护，设计实现时保留。

## E．临近到店、加速与提醒

产品要求：理想到店前30分钟内请求每60秒采集，前15分钟内请求每30秒；多人同店共享最紧迫采集要求。页面30秒读取副本与来源采样频率分开，30秒刷新页面不证明已开启30秒源采集。

后续提醒内容至少包含：门店／队列、本人的当前预测、比计划提前多少、建议动作、依据更新时间。对已错过合适重排时机的情况，后置版本给提前到场建议，不直接取消旧号。

用户可理解的状态包括“追踪中”“临近到店，正在更频繁更新”“预测提前，请核对并考虑早到”“数据暂不可用”“提醒权限未开”“已发送／送达未知／发送失败”。这些状态必须由真实功能返回；现在尚未实现的系统推送不显示“已保障不漏号”。网页关闭或手机后台时是否还能提醒，按实际渠道能力说明，不承诺浏览器总能后台运行。

结束追踪与取消官方排队分别设计；核心v1只结束本项目追踪。自动取号／取消／重排是后置业务，不摆可执行按钮，也不拿样式状态模拟真实操作成功。

## F．用餐记录

正常取号、签到、首次有效叫号、入座和结束是不同时间。记录页允许精确时间、大约范围、未知及后续修订；用户不记得时无需强填。不将公开展示消失自动填为叫号，不把“结束追踪”填为取消／入座，也不把重复记录变成新的独立样本。

告知用户这些记录用于改进预测，个人号单／行程保持私有。rc67已有浏览器私有草稿、下载全部修订、从本机恢复及独立接收命令，没有公共提交接口；下载、本人确认保存、实际首次接收、人工审核分别显示，不把表单发送到公共只读统计地址。换统计门店不改变已有经历范围，新增事件后须重新下载，未知时间不强填。

## 数据入口与隐私边界

当前公开网页允许的内容接口如下。设计者不能为了方便增设个人号单、管理或上游代理路由。

| 接口 | 已有用途 | 注意事项 |
| --- | --- | --- |
| GET /api/v1/days | 当前日历及已保存汇总 | days按日期／店号组织；可能包含后台加载进度 |
| GET /api/v1/months/YYYY-MM | 指定月份汇总 | 未加载／不可用门店显式保留，不能补零 |
| GET /api/v1/stores/店号/days/YYYY-MM-DD | 所选门店当天有界曲线 | 检查请求店号、日期、接收时间、截断和状态 |

这些接口只读已保存副本，不新增寿司郎查询。当前网关不接受查询参数、写方法、管理接口或任意地址；/monitor是内部页面，不放到公共导航。数据结构以dailyview.py、dailyarchive.py、monitorhub.py及网关代码为准，本规范不新建接口。

当前公开参考实验的私人号码／取号时间只在浏览器内存，不写URL、请求体、访问日志、localStorage或公开统计。关闭页面不保存；若以后需要跨设备、后台追踪或持久保存，应接独立私人访问服务并更新数据说明，不能静默改为公开上传。AI仅接收允许的公共摘要，不接受个人号码、私人行程、凭证或结果原文。

## 文案及设计交付检查

所有页面内容须能回答：这是哪家店、哪种队列、哪一天、数据多旧、当前能做什么。普通文案使用“读取失败／数据较旧／资料不足”等，不把error_code、schema或策略名直接展示给用户。

写出每个输入的必需条件、未知值和错误提示；每个数字的单位、时间依据及模型状态；每个按钮的真实作用和是否已实现。示例数字明确标成设计示例，不流入真实统计。没有接好的页面先交内容设计，不伪造在线能力。

交付时说明对应本规范的A–F哪些区域、所依托现有文件和还需后端提供的字段。更新本板块版本与完整交接历史即可；无需因纯设计文案重复执行整个代码测试。


## rc66实现同步

本地源码已有同店过去日曲线初估与实时修正，仍标“参考实验”，不是已校准的真实叫号。区分“历史加载中”“历史初估”“历史＋实时修正”“历史不足／仅近期趋势”与“较晚端尚不确定”；不足不补零、未知上端不显示成午夜或1970年的时间。历史请求只读公共曲线，号码与取号时间不上传。陈旧／失败／倒退时撤回结果，不在旁边写仍按实时趋势计算。源码实现不等于云端已更新；发布日期和部署状态按完整交接记录核对。
