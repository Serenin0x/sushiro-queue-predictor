# 版本路线与交付边界

2026-10-12，根据用户提出“0.2.0范围是否太多，应把任务分配到0.3.0及以后”的最新要求，收敛版本范围。当前源码仍为 **0.2.0rc83**，正式0.2.0尚未发布。本文件安排产品交付，未完成的规划不能当成已实现功能；最新事实和编辑历史见[项目交接](PROJECT_HANDOVER.md)。

## 分期交付

| 版本 | 主要交付 | 发布时必须有的结果 |
| --- | --- | --- |

| **0.3.0 · 稳定运行与重点扩店** | 多日质量报告、故障定位与告警、受限恢复、存储容量和备份完善；优先北京、成都，先扩店再分阶段调整频率 | 先固定本次观察范围与窗口，再报告覆盖、缺口、失败与恢复；扩店和频率变更分别评估。电脑实际离线期间的对照与主机重启恢复实测归本阶段，不再挡住0.2.0 |
| **0.4.0 · 已有号码预测试点** | 用户输入已取号码；历史初估随实时变化修正；日期／时段分层、快速推进分析、预测轨迹和区间；正常用餐结果记录 | 分开报告展示位置情景和实际叫号预测；时间顺序回测不借未来信息，真实结果可追溯。无标签或数据不足的门店保留未校准／不可用，不能虚报误差精度 |
| **0.5.0 · 大模型融合与用餐规划** | 可替换的低成本大模型、同店共享计算和调用预算；输入理想用餐时间与偏移，比较候选时间及风险 | 本地算法与有／无大模型结果同期对照，记录延迟、费用、失败回退；保留+10／-10语义。即时取号假设和建议取号时间须有可验证资料，不伪造当前发号尾部 |
| **0.6.0 · 防过号与通知** | 接通同店共享的临近用餐监控：前30分钟60秒、前15分钟30秒；异常加速重算、提前到场提醒及可用通知入口 | 实际采集频率、上游新鲜度、提醒触发与送达分别验证；陈旧或失败时暂停预测。同店用户共用采集，不因人数增加重复查询 |
| **1.0.0 · 核心产品版** | 整合统计、手动号码追踪、两种预测及偏移、可解释误差、日期规律、大模型与防过号提醒；明确门店能力等级 | 对已验证试点完成真实用户流程和预测／提醒验收，范围与精度如实标明，部署与交接完整。全国目录、实时覆盖、预测覆盖分别说明 |
| **1.0以后 · 个人业务自动化** | 逐号发放时间研究、精确个人位置、自动取号、取消与重排 | 独立核对接口与业务规则、正常授权更新、操作对账、取消后重取失败及人工接管；不作为核心1.0的发布前置 |

已有源码中的模型、追踪和AI适配器继续保留为实验能力，按后续版本验收；分期不是删除代码，也不是将实验能力提前宣传为正式功能。年度、季节与特殊节假日规律随可用数据积累，不能为了凑版本日期宣称已经学会未观测的规律。

## 0.2.0怎样收尾

只使用[冻结清单](V0_2_ACCEPTANCE.md)判断完成。2026-10-12用户同意不等待人工关机对照，G4转为后续观测并保持“未实测”；既有闭店／次日开采检查继续自动执行。随后整理最终版本信息、安装包和该提交的必要检查，创建正式标签与Release。已通过且未修改的接口对照、恢复试验和检查不重复做；新故障仍须修复并记录，不能用改版本范围掩盖故障。

不再把72小时／更长连续运行、147店或全国恢复、主机重启、五分钟采样、预测精度、付费AI、通知和自动业务增加为0.2.0发布前置。它们按表中对应版本继续推进。更长观察可与功能开发并行；每次观察在开始前固定范围、结束条件与质量指标，不无限续长同一轮验收。

原目标面板文字仍包含电脑离线标准，工具不能编辑文字；执行时采用用户本次最新决定，不继续要求人工离线作为发布前置，也不宣称该试验已通过。任何版本规划都不自动扩大既有账号权限、采集门店、请求预算、频率或访问期限；当前三店十分钟有限试验保持，延长运行或扩店在进入相应阶段时落实具体计划。

## 后续开发者的执行规则

1. 先核对当前版本的冻结清单，解决其中未完成项；新功能归后续版本。
2. 每个工作包分别标明设计、实现、实际运行和已发布状态；源码存在不代表已上线。
3. 版本需求发生变化时更新本文件、对应验收文档、README与四板块交接，保留旧决策的日期和变更原因。
4. 正式小版本发布后，用补丁版修复已有能力的故障；下一组新能力使用下一小版本，不长期堆叠0.2.0候选号。
