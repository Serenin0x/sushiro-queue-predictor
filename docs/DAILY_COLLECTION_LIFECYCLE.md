# 每日营业采集、历史月份与接续部署

2026-10-09：rc61 源码已实现每日控制器、只读月份与 CLI，合成跨日和重启检查通过。当前云端仍运行 rc57 的原有限试采；新机制尚未部署，不能用软件检查代替完整全天、第三天接续或 72 小时真实验收。现有采集、数据、预算和原截止时间均保持。

## 每一天怎样运行

1. `DailyController` 对显式单店根目录持有一个独占锁，等待指定 `not_before` 和当天营业窗口。默认规则来自用户假定，单店／日期覆盖优先，未知年份的节假日不猜测。
2. 进入窗口后冻结当天任务：创建时间、当日最后闭店之前的截止、当天营业表及预算。基础间隔 60 秒；预算为全天营业格数、各营业段边界余量和 3 次恢复余量，上限 1500 组。请求为两次分开的 GET，最多 3000 次／店／日；不保证源每分钟更新。
3. 重启恢复同一天的原身份、期限与预算，保留完整间隔屏障。断网后只查询恢复当时的当前状态，不补发错过的历史采样。每天重新建立任务，绝不续改旧试验来假装每日运行。
4. 终态原始窗口保持；关闭时写入不可覆盖的 `projection.json` 和 `result.json`，后者记录前者的 SHA256。归档后的父检查点记录完成日期；中间断电时可核对同一文件并继续完成归档，不额外查询来源。
5. 控制器等待下一营业日。内存中的 `DailyView` 只保存当前一天，历史月份通过明确日期读取归档，最多 31 天；不会碰到旧单任务 16 日期限制，也不无限扩内存。

规则是自然周一至周五 11:00–22:00，周末／已知节假日 10:30–22:00。每日截止按毫秒创建时刻加整秒持续时间冻结，可能比声明闭店提前不足 1 秒；每个实际 GET 仍再次核对营业窗口，第一请求跨闭店时第二请求会被阻止。午间休息段不采集。跨日缺口计数是自然日期差，不代表这些日子都应当营业。

## 保存与读取

专用根目录为 0700，文件 0600；每日目录结构为：

```text
store-root/
  controller.json
  controller.json.lock
  YYYY-MM-DD/
    plans.json
    campaign/             # 原始逐窗口任务及 SQLite，保存全部返回数组
    projection.json       # 每次时间与按原顺序的前三位、数量、错误和覆盖
    result.json           # 当天任务结果与投影哈希
```

只读服务从采集进程的已提交副本读取当前一天；历史曲线验证日期、店号、语义和归档哈希后读取。月份摘要缓存最多 62 天，不缓存整月曲线；文件身份、大小、权限和修改时间变化时重新核对。哈希是本项目保存一致性的检查，不是官方签名或异机备份。完整原始数组仍在 SQLite，不因为图表截断而删除。

新增命令：

- `remote-daily-collect`：持续运行单店每日控制器，SIGINT／SIGTERM 正常停止；重新启动从私有检查点恢复。
- `remote-daily-serve`：相同采集加本机只读页面，只监听回环地址，需要安装已有 `server` 可选依赖。
- `remote-daily-status --root …`：离线读取最后检查点，不联网、不抢写者锁，不把保存状态当进程存活。
- `daily-archive-month --root … --store-id … --month YYYY-MM`：只读选定月份，缺少归档与无法核对分别报告。

页面保留 `/api/v1/days` 当前月份、指定店铺日期详情，新增 `/api/v1/months/YYYY-MM` 与内部单店月份接口。月份切换后只接受当前选择的响应；旧服务不支持月份路由时仅在 404 回退其现有索引，其他错误不会当无数据。个人号码输入仍只在页面内存，不加入月份请求。

汇总配置使用明确新 schema2／`daily_controller_readonly`，每个回环工作者对应一店，最多 16 个。旧 schema1 的有限截止仍有效；新模式没有延长旧任务。公开网关仍仅开放统计资产、月份和已配置门店的日详情，不开放个人号单、状态管理、文件下载或写方法。

## 旧试采归档的只读衔接（rc62 本地候选）

现有有限试采的副本格式为 `daily-exports/YYYY-MM-DD/store-ID.json` 与同日 `manifest.json`。新服务可显式提供 `--legacy-exports-root` 和 `--legacy-through-date`，两项必须同时指定；旧导出所属最后日期必须早于新 `not_before` 对应的北京时间日期，两个根目录不能相互包含。部署准备工具也接受这两项，并只赋予新采集根目录写权限。尚未产生的旧导出目录不会被创建。

选定月份中，截止日期以内只读取原 manifest 和当前店副本，之后读取新每日归档。核对唯一店号、日期、原 SHA256、点数、原摘要及原导出时间；保留原 `generated_at` 和每个采样时刻，不导入数据库、不生成新的接收时间，也不发来源请求。缓存同时检查 manifest 与副本身份变化。旧副本的完整投影标记不等于完整全天或官方叫号认证，原 `full_day_source_quality_verified=false` 保持。

旧日期如果也存在新归档，即使新文件只有一半，报告日期冲突，不选择较大数字或拼接两份。导出失败行、损坏、摘要不符、越权字段、权限／符号链接异常及读取中修改都保持不可用；两份文件均不存在才报告缺失。接口附带无私有路径的归档来源说明。该能力已有本地合成及原导出工具契约检查，真实旧副本和云切换仍待验收，不因软件兼容就宣称完成接管。

## 失败与接管

短暂网络／502／503／504 沿用最多 3 次恢复，保留失败窗口，退避与当天预算不变。鉴权、限流、证书、结构异常、未知请求、归档冲突等会停止该店控制器；下一天不会自动复活这个失败，需核对原因。每组请求开始前检查至少 1 GiB 可用磁盘余量，压力不足持久化停止，不自动删旧数据；其他进程并发占盘仍可能导致实际写失败，不能承诺磁盘绝不耗尽。

独占只覆盖这个显式根目录；不同根目录、旧试验或其他主机的同店写者不会被发现。部署必须先核对同店旧写者正常停止，并选择新的 `not_before`；不能同时启动新旧采集来“接续”。丢失控制器但已有日目录时拒绝新建，不重置当天预算。规则／配置变化需要单独核对，不能覆写旧检查点。

`deploy/prepare_daily_native.py` 仅生成十二店 systemd 单元和新只读汇总配置，不安装、启动服务，不改防火墙或创建凭证。使用已核验 release 中的 CLI 和营业表，要求新空根目录、未来明确接管时间；新端口与旧监听分开。运维登录完成后应核对安装版本／原写者／空间，安装新服务，观察开店、闭店及第二天，再切换现有统计入口并安排健康检查和异机备份。

## 已验证与未验证

合成检查覆盖：连续 17 日期、闭店／接管前零请求、晚启动无补发、重启原期限预算、跨日先封存旧任务、午间休息、第一响应跨闭店、同根重复写者、丢失检查点、时钟倒退、鉴权失败次日不重试、瞬时恢复保留失败、磁盘压力、归档中途断电和冲突、缓存失效、只读月度／ASGI／CLI 及新旧网关范围。

真人等待标签、实际叫号误差、源新鲜度、数量单位与全年日期支持没有因此自动通过。新控制器目前仅基础背景采集；本人临近用餐的动态 60／30 秒需求需接续既有共享计划机制，不能声称这份空 `plans` 控制器已经实现加速提醒。完整 v1 继续：历史初估＋实时模型、真实误差、理想时间、受限 AI 和防过号提醒。见[主交接](PROJECT_HANDOVER.md)、[核心范围](V1_CORE_SCOPE.md)和[营业门控](BUSINESS_HOURS_COLLECTION.md)。
