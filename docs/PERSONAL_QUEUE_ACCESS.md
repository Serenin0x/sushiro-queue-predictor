# 个人票据与实时排队位置：已验证通道和接入顺序

2026-10-07 已用本人正常小程序会话，独立读取当前排队票据和该票据的状态历史，两次只读 GET 均 HTTP 200。这是本机接入研究，尚未交付公开 CLI、自动取号或正式的精确排位功能；版本仍为 0.2.0rc42。完整操作、授权和限制见 [PROJECT_HANDOVER.md](PROJECT_HANDOVER.md) 的 E0280。

## 要区分的四种信息

| 信息 | 当前证据 | 如何使用 |
| --- | --- | --- |
| 我的号单 | 官方界面与独立响应的号码、门店一致，人数、桌型、取号日期/时间及签到状态可读 | 建立个人跟踪记录；公开采集仍按门店共享 |
| 我前方实际等待桌数 | 还没有证实直接返回此字段 | 有明确字段及桌型/签到范围时优先采用；否则输出估计与误差 |
| 现在重新取号会得到的队尾号码 | 现有两个匿名接口的完整响应没有此字段 | 先找发号/队尾只读数据；一次已有号单只能提供取号当时的号码观测 |
| 票据状态事件与时间 | 状态历史已读，但本次只有 WAITING，时间戳没有时区 | 保存原始事件及接收时刻；不自动解释成叫号或入座结果 |

即将叫号三位是有限展示。自己的号码减去展示最大号码，会混入未签到、弃号、返签、不同桌型、预约与号码后缀等因素，不能称为精确的前方桌数。门店汇总等待数量也不能自动当作个人排名。

## 当前小程序的正常查询

固定来源为 `https://sapi.sushiro.com.cn`：

| 正常操作 | 实际观察到的请求 | 本项目验证 |
| --- | --- | --- |
| 会员中心 → 预约情况确认 | GET `/gateway/wechat/api_auth/2.0/ticket/status`，没有 query 参数 | 正常请求 200；电脑独立一次 GET 200，号码及门店与本人界面相符 |
| 查看排队号码 | GET `/gateway/wechat/api_auth/2.0/ticket/statusHistory`，query 为 `ticketId` | 正常请求 200；核对 ID 属于上一步的本人票据，再独立一次 GET 200 |
| 号单中的门店信息 | GET `/gateway/wechat/api/2.0/getStoreById`，query 为 `storeId` | 本轮观察到正常 200；此前公共门店查询另有独立证据 |

最新官方请求与两个参考项目的旧代码有区别：当前状态查询没有旧版 `wechatId` 参数，历史查询为本次新发现。不得根据旧源码猜写接口，也不得把公共查询上下文当作个人业务权限。

本轮个人会话的 JWT 声明寿命为 3600 秒，签名未由本项目验证；只证明该会话在两次实际 GET 时被服务接受。声明到期不等于所有账号、接口和版本均有固定一小时寿命。正常客户端如何自动更新、电脑退出后跨到期恢复、服务器个人查询供应仍需验证，不能把匿名门店通道的长期成绩套过来。

## 响应字段及未确定语义

当前响应顶层明确存在 `netTicket` 与 `reservationTicket`；本次前者有值、后者为 null。个人排队对象包含 `TICKET_DETAIL`、`STORE_INFO`、`TICKET_TYPE`。

| 字段 | 实际观察 | 暂定处理 |
| --- | --- | --- |
| `TICKET_DETAIL.number / storeId / ticketId` | 字符串号码、字符串门店 ID、整数票据 ID | 私有身份关联；历史请求只能使用当前本人返回的 ID |
| `status / checkedIn` | 独立查询为 WAITING / true；正常界面显示“签到中” | 原始业务状态与签到布尔值分别保留，不当作已叫号 |
| `queueDate / queueTime` | 字符串；界面可读取号时间 | 保留原值，核对时区、是否变更及事件意义后才作时间标签 |
| `tableType / numAdult / numChild` | 字符串桌型及人数 | 为匹配桌型与人数提供条件；不转发 LLM |
| `TICKET_DETAIL.wait` | 整数，与同次 `STORE_INFO.wait` 不相等 | 两种值分别保留，单位、计算时点与含义尚未验证 |
| `STORE_INFO.waitingGroup / waitingGroupTable / waitingGroupCounter / waitingGroupPair` | 本轮响应存在整数值 | 候选排队负载/桌型线索，尚未证实是个人前方桌数或是否只含签到者 |
| `ticketStatusHistory[].status / timestamp` | 一条 WAITING；时间可解析但没有时区 | 不猜时区，不映射为叫号、过号、入座或人工确认结果 |

现有匿名 `groupqueues` 完整 JSON 只有五个数组：`reservationQueue`、`counterQueue`、`boothQueue`、`storeQueue`、`mixedQueue`；`storequeuecount` 是单个整数。2026-10-07 对试点各一次 GET 全 200，确认不是本项目白名单隐藏了队尾字段。该结论限定这两个地址和本次响应，不排除其他正常接口提供更多信息。

## 产品接入顺序

1. 先接个人状态只读提供方，凭证与公共采集分开；号码、票据 ID、手机号及个人行程只入私有存储。数据失效时保留最后接收时间与失败原因。
2. 把状态历史与公共门店快照对应起来，分别记录实际事件时间、首次获取时间和适用桌型。核实出现真实叫号/过号事件后，再讨论减少人工结果记录；本轮真实训练标签仍为 0。
3. 核对等待值、分桌型数量、取号时号码及实时变化，评估它们是否改善两种预测。缺少真实前方桌数时给区间和数据限制；目标时间的反推还需要新取号位置的模型。
4. 接入本人自动取号时，先只读查已有号单，再按明确人数、桌型和手机号要求提交一次；结果不确定就对账，避免重复提交。保护正在等待的已有号单，不能只为了观测队尾反复出票。取消、重排和自动提前提醒按原完整需求继续验收。

用户已明确授权在本人账号进行自动取号功能和正常测试，旧历史中的“未获取号测试授权”不再作为本轮停止理由。当前保留已有票据，未新取号、签到或取消；“爽约没问题”仍只是用户的看法，本项目没有确认该规则。

原始响应、捕获会话、票据标识及精确个人时刻未进入仓库、公开报告或 LLM。本轮调试限定原授权的 sapi 单域名，限时保护关闭解密，最终核验三项临时开关均关闭并恢复原名单。后续接入应使用已验证的独立数据查询；画面识别仅作为字段核对辅助。
