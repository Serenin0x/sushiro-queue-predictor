# 长期日期参考档案

rc52补齐[短期展示变化参考](TREND_PROFILES.md)的长期保存与选择入口。一个短期文件最多96个完整窗口，默认30分钟网格只覆盖约48小时跨度；长期档案汇入多个明确封存参考，按当前日型、周几、时段、月份／季节选择研究样本。它不生成叫号标签、不估真实过号率、不把排序转成等待分钟；认证真实结果仍为0、`eta_available=false`。

## 不可变档案与首次汇入

每份档案保存独立UUID、修订、上一内容哈希、创建时刻、固定门店／规则范围，以及全部已汇入的原始短期参考与本次程序接收时刻。创建和追加都完整校验输入后产生**新文件**，旧档案及来源文件保留；不覆盖旧文件、不重置首次接收或静默删去较早资料。同一原始参考重复汇入不新增、不改变修订和接收时刻。不同来源重复包含相同窗口、相同统计时只计算一次；同窗口有不同统计时整批拒绝。

一次最多16份原始参考；整个档案最多512份、24,576个不同窗口、4MiB，超限拒绝而不截断。所有来源须是schema1原始参考且具有相同门店、窗口、缺口／覆盖规则及信息可用依据。不同店、不同窗口、严格首次接收与封存重建不得暗中混合。已选取的schema2文件不能再当原始观察汇入，以免重复挑选后扩大证据。

`local_first_receipt`与显式`sealed_response_reconstruction`的区别继续保留：后一种只从现在封存以后用于前瞻研究，不能声称过去预测当时已经收到。档案再记录**首次汇入档案**的时刻，晚汇入的旧参考不会提前进入较早查询。该时刻、UUID和内容哈希是本机结构证据，不认证数据来源或实际叫号。

读取只访问明确指定的私有普通文件，检查权限、非符号链接、大小和读取前后文件身份；不搜索目录、打开活SQLite、读凭证或联网。输出文件0600／目录0700，沿用完整新文件提交及持久化确认；不能因确认失败删除已提交输出或覆盖旧档案。档案独立于当前采集任务，不自动收集新文件或启动常驻上传服务。

## 日期匹配与均衡选择

每次选择先核对全部档案，包括当前截止之后接收的资料，损坏或冲突不因“尚未用到”而忽略。之后只保留在目标时刻前已汇入、且结束在目标窗口开始之前的不同窗口。采样平均可比间隔仍须在当前间隔的0.8–1.25倍以内；日期由当时可用日历公告生成，未知日历保留未知。

沿用五层匹配：日型＋周几＋小时＋月份；日型＋周几＋小时＋季节；日型＋小时＋季节；日型＋小时；日型。各层保留相同节假日名称，默认至少8个窗口及2个不同当地日期。选择不使用消失数／变化速率来挑样本，避免先挑“快号”再宣称当前异常。

每个匹配层将窗口按当地日期分组，默认每日期最多8个、总数最多96个。若合格日期多于总上限，均匀选取覆盖完整时间跨度的日期；再以轮转方式分配各日配额，在该日时刻排序中均匀选择，单配额取中间窗口。不会只取最近96行，也不会让采得特别密的一天独占参考。上限取满后仍报告完整合格资料数，不足8窗／2日期继续向较粗层尝试，仍不足则为空。

这些是明确的研究抽样规则。输出排序描述**本次选择的参考**，不是整个档案的客流频率或未来风险概率；时间依赖、选取偏差及采样展示饱和仍需真实资料评估。不同月份或季节可以被保存和匹配，不代表目前真实资料已经覆盖一年。

## 可审计的schema2参考

选择结果保留原始五列窗口格式及全部规则，另绑定档案内容哈希／修订、目标时刻与可比间隔、匹配层、当时已知资料数、完整匹配窗口／日期数、实际选取数、配额和最低条件。全部纳入参考文件内容哈希，字段和交叉算术严格校验；schema1仍可读取。

选择文件实际创建后才能用于新的当前观测，不能回填旧预测。查询目标所匹配的日期属性改变时返回`reference_target_changed`；未知、过时、停止或样本不足不产生零等待或假百分位。完整档案、窗口数组、文件路径、UUID及档案哈希不进入[公共AI请求](DISTRIBUTION_FUSION.md)，仍只注入四个聚合数值字段。

## 手动研究入口

以下时间、路径和资料为示意。先让来源采集自然结束、确认数据库闲置，按[短期流程](TREND_PROFILES.md)为不同日期生成原始参考；不对当前六店活库操作。

```sh
sushiwait trend-archive-add --profile-file references/day1.json \
  --profile-file references/day2.json --output archives/revision1.json

sushiwait trend-archive-add --archive-file archives/revision1.json \
  --profile-file references/day3.json --output archives/revision2.json

sushiwait trend-archive-select --archive-file archives/revision2.json \
  --reference-for 2026-10-08T08:00:00Z --cadence-ms 300000 \
  --output selected/current.json
```

`--cadence-ms`是当前平均可比间隔，不是覆盖总时长；默认300000对应5分钟。schema2在实际创建以后，须用新鲜且相匹配的下一份公共上下文执行`trend-score`，不能拿选择前已到期的输入。标准输出仅报告保存／持久化、修订与参考数量，不输出私有路径或号码。

## 自动追踪中的动态选择

新启动的[自动追踪后台](TICKET_TRACKING_LOOP.md)可重复给`--trend-archive-file`，每店一份、最多3店；与私人会话目录分离，范围及结构在工作线程开始前校验。相同店不能同时配置静态参考和长期档案。档案启动时读取一次、固定为内存快照，不热更新、不自行导入目录。新增资料需明确使用下一档案版本启动新的追踪过程，不重置原采集预算／截止或私人号单的有效范围。

后台先从同一份写者投影整理当前日期与可比间隔，选取参考后以稍后的本机时刻再次整理**同一份已复制投影**，使选择的实际创建时间不晚于新观测；没有第二次门店GET，不将读取时钟伪装成源更新。同一轮、相同档案／时间网格／日期属性／可比间隔共用一次选择；个人号码、条件剩余和提交版本仍各自处理。跨日期／时间网格／间隔变化或下一轮会重新选择，不跨这些边界回用旧参考。

```sh
sushiwait ticket-track-run --state-dir personal/state --store-id 900001 \
  --collector-url http://127.0.0.1:8765 --duration 3600 --max-cycles 720 \
  --trend-archive-file archives/revision2.json
```

900001是合成店号，不可用它访问真实门店。当前rc43／rc45六店任务保持原版本和300秒、原期限及预算，没有因新源码升级／重启，也没有新追踪路由。此组件仍未在产品页面展示、没有实际付费模型请求或通知。

## 验证与下一步

专项以真正私有文件、CLI和后台线程检查：数月档案、完整输入与晚收到资料、重复／冲突、不同日型／节日／间隔、配额和均衡日期、来源选择与速率无关、容量及不覆盖、公共隐私与同店两人共用一次投影／参考选择。最大规模合成档案含256原始参考、24,576个窗口，选取96个不同日期参考；本机一次选择约0.476秒。这是单次合成处理耗时，不是生产延迟保证或模型精度。

安装版、Linux、真实封存资料导入、精确公开与CI以[交接文档](PROJECT_HANDOVER.md)中的实际结果为准。下一步仍要积累自然结束的跨日型资料、正常用餐结果，训练实时等待情景并校准误差，比较同一时间切分下有／无AI的数字与成本；长期档案本身不能替代这些验收。
