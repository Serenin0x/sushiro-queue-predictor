## 1.2 项目来源与目标

项目对外展示名为全大写 **SUSHIWAIT**；GitHub 仓库名保留 **sushiro-queue-predictor**。用户最新提供 Aliment 字体包，要求使用 Light 字重，并明确接受字体轮廓 SVG 标题、必要时高清图片；本机私有 SVG/高清 PNG 预览已完成并展示给用户，公开许可或替代字体选择正等待用户回复。当前公开 README 仍为原生 SUSHIWAIT 文字标题，字体资产未发布。最新标题工作不属于独立 Logo 制作，不改变 R19 后期 Logo 顺序。此前 SushiWait 和默认 sans-serif 方案的历史保留，见 E0019–E0021。README 按最新偏好详细介绍产品价值，文字可以有吸引力，现有工具与明确标为规划的未来体验分别介绍，后续随系统更新继续改进；不得虚构已上线能力、误差或稳定覆盖，后续接手不得自行改名。

用户希望建立一个针对中国大陆寿司郎门店的排队预测和辅助排队系统。用户目前能够通过寿司郎微信小程序查看门店的实时排队信息，并希望把这些实时信息连续采集到自己的服务器，再与历史统计、日期类型、季节趋势及外部事件结合，预测叫号时间、安排取号时机、监控过号风险。

最终产品目标：

- 支持用户选择中国大陆任意寿司郎门店，并逐店显示数据、预测和操作能力是否已验证。
- 支持“现在取号，预计何时叫号”和“输入理想时间，规划何时取号”两种预测模式。
- 给出预测误差或时间区间，避免用一个没有校准依据的精确时间误导用户。
- 支持服务器持续监控、防过号提醒、叫号异常加速分析。
- 在接口能力、规则和用户业务授权满足条件后，支持自动取号，以及受控的取消后重排。
- 纳入工作日、普通周末、具体星期、调休、特殊节假日、月份、季节、门店和时段等差异。
- 将大语言模型作为结构化外部信息处理与解释模块，引入实时预测流程，并验证实际收益。
- 在 GitHub 开源，持续维护足够完整的交接材料。

这不是寿司郎官方项目。用户要求的目标产品也不等于参考项目的现有能力；尤其不能用香港地区的接口或字段直接推断大陆小程序行为。

## 1.4 数据接入方向与证据范围

首选验证方向是：研究小程序使用的后端请求协议，在具备相应访问权限后，由服务器直接查询实时结构化数据；投屏用于核对页面含义、字段对应关系和变化时间。历史统计是对实时采集的补充，不是实时采集的替代品。

需要区分两条通道：

- **门店状态通道**：门店目录、堂食/预约展示号码、已签到桌数等。是否需要应用查询鉴权、是否缓存、允许调用频率、源数据更新时间，均需真实验证。
- **个人号单通道**：本人号码、人数、桌型、签到、取消、叫号、过号等状态。需要寿司郎的业务授权，不会因为用户在我们的小程序里登录微信就自动获得。

## 2.2 时间语义与两种预测

时间输入必须明确区分以下概念：

1. **理想到店时间 `desired_arrival_at`**：例如 18:30。
2. **叫号偏移 `call_offset_minutes`**：按此前对话确认，`+10` 表示希望约 18:40 叫号，在 18:30 到现场后等待约 10 分钟；`-10` 表示希望约 18:20 叫号，即比理想到店时间早 10 分钟。后一设置必须结合门店签到和过号规则评估可行性，不默认存在宽限。
3. **可接受窗口 `acceptable_early_minutes / acceptable_late_minutes`**：用户可以接受比目标叫号时刻早/晚多少分钟。它是用户偏好，不是统计误差。
4. **模型预测区间**：模型基于数据给出的不确定性范围；需独立显示并持续校准。
5. **实际入座时间**：若用户目标是开始吃饭，则还须估计叫号到入座的延迟。交互应明确目标是哪一个，不把到店、叫号和入座混称为“用餐时间”。

目标叫号时间的规划关系为：

```text
target_call_at = desired_arrival_at + call_offset_minutes
```

两个模式：

- **现在取号**：先预测当前取号的等待分布；成功取号后，改为预测这个真实号单的叫号时间及状态。不能仅因用户查看预测就实际取号。
- **理想时间**：预测未来不同取号时刻对应的叫号分布，选出建议取号窗口，并随数据更新重新评估。不能只做“目标时间减去当前等待时间”。

界面可以展示“预计 18:40，区间 18:28–18:53”等示例样式；没有真实校准结果时，不能给这些示例冠以已经验证的 80% 或 90% 覆盖率。

## 2.3 防过号采集与监控

用户明确要求的最低目标监控节奏如下。它是产品设计要求，是否能在真实源接口上按此节奏实现仍需验证。

| 时间与状态 | 目标查询周期 | 说明 |
| --- | --- | --- |
| 距用户设定的用餐时间超过 30 分钟 | 基础周期待试点确定 | 服务端持续监控，避免无意义重复请求 |
| 距用餐时间 15–30 分钟 | 60 秒 | 边界到 30 分钟时进入此档 |
| 距用餐时间不超过 15 分钟 | 30 秒 | 边界到 15 分钟时进入此档 |
| 目标时间已过、计划仍在等号 | 30 秒 | 直到叫号确认、取消、过号或计划结束 |
| 发现异常加速或预测显著提前 | 提前进入较高频档 | 即使距离设定时间仍超过 30 分钟，也触发风险重算和提醒 |

仅围绕设定用餐时间计时会遗漏提前叫号，因此还必须根据预测区间的较早端、当前号码状态和异常速度提前触发。触发阈值及是否需要更高频率由试点结果与源接口额度确定；未经验证，不宣称 30 秒周期能保证防止所有过号。

每份数据至少区分：

- 请求开始时间、响应接收时间、源数据更新时间（有则保存，没有则未知）。
- 实际采集成功时间、缓存/旧数据标志、错误与限流状态。
- 数据来源、门店、队列类型、字段版本和可观察能力。

成功发起请求不等于收到新数据。若上游本身有缓存或延迟，界面和模型不得把旧数据标为刚刚更新；数据不足时应降低可靠程度、扩大区间或暂停自动操作。

同一门店、同一数据通道按关注用户所需的最高频率共享采集，避免每个用户各发一份相同请求。门店通道与个人号单查询分别调度；需有全局和逐门店限流、超时、退避与异常恢复，不通过叠加账号或地址规避服务限制。

## 2.4 跳号、过号与号码推进的证据口径

历史分析至少按门店、人数/桌型、队列类型、具体星期、工作/休息日、节假日与假期日序、下午/晚间时段记录推进强度、异常出现时间、持续时间和恢复过程，并结合月份与季节长期变化。

必须保留以下区分：

- **号码推进或展示集合变化**：在两次快照之间观察到的号码、顺序、签到桌数变化。
- **跳号强度**：在已验证号码规则下，对推进变化的统计描述。
- **真实过号、主动取消、弃号、正常叫号**：只有事件或本人状态等可靠证据支持时才分别归因。
- **过号率**：须先定义可观测分子、可观测分母和观察窗口。只有三位展示号和聚合桌数时，通常不足以识别全队列真实过号率；只能输出可观测替代指标及其局限。

堂食三位已签到展示号的最大值不等于全店处理到的号码；预约三位号码也不等于普通堂食进度。不能简单计算“自己的号码减去展示最大号”得到等待桌数。不得混合不同号码前缀、分队列、日内重置和跨日记录。

近期几分钟的变化与同日期、同门店、同时段的历史基线比较，用于识别突然加速。具体算法可包括稳健速度估计、异常检测和状态切换模型，选择应基于数据质量与回测，不预先承诺某种复杂模型一定更好。

发生突然加速时，需要重新计算完整叫号时间分布、风险和可行动建议，并在通知额度内及时提醒。采样间隔内发生的事件只能记录为时间范围，不编造精确秒级发生时间。

## 2.5 预测和数据验证原则

首期候选方案是可解释基线与分位数模型，尚未实现或选型冻结：

- 对照基线：官方显示等待时间（若可用）、相似日期/时段历史中位数、近期可观察队列变化推算。
- 候选主模型：LightGBM 等分位数模型，联合门店、桌型、日期、实时和长期特征。
- 区间校准：根据时间序列验证，检查实际覆盖率与区间宽度。
- 新店和数据稀疏门店：借用相似门店信息，但标记冷启动并扩大不确定性。

权重和参数应由时间顺序的真实验证决定。节假日、月份和季节规律需要对应跨度的数据；短期试点不能证明全年度预测可靠。

关键数据：门店资料、持续快照、可获得的号码事件、用户实际结果、外部日期与事件。真实叫号时间和入座时间比重复快照数量更有价值。取消时间不能当作叫号时间；未完成排队是删失结果；自动重排造成的选择偏差需在评估中考虑。

评估至少包括：平均绝对误差、较大误差分布、预测区间覆盖率/宽度、按日期/门店/时段的表现、过号风险和到店后真实等待时间。切分训练与测试按时间先后，不能把同一号单的相邻快照放入两侧导致泄漏。

## 2.6 自动取号与重排原则

自动取号、取消和重取不是只读采集。它们需独立的用户授权、经过验证的业务登录状态和门店能力规则。用户在当前对话授权的是立项及创建 GitHub 项目，**尚未授权本项目对真实寿司郎账号执行取号、取消或重排**。

规划控制状态包括：等待取号、取号请求结果待确认、已取号监控、重排评估、取消结果待确认、重取结果待确认、已叫号、已过号、已取消、暂停需处理、已完成。以后设计状态机时必须明确允许的转换与恢复行为。

调度器比较：

1. 保留当前号码的叫号分布和过号风险。
2. 现在取消后重取的叫号分布、取号资格和失败风险。
3. 稍后重排的可行窗口。

若当前号码预计提前约 20 分钟，而重排将明显过晚，应保留当前号码并提醒用户提前到店。最迟到达时间必须依据门店真实签到/过号规则及预测不确定性计算，不假定统一宽限时间。

重排需要稳定的数据、持续多次的改善证据、用户设置的风险与次数边界、冷却时间及门店明确允许的重取规则。可考虑首轮试点最多重排一次，但这是待验证的实施方案，不是最终已批准的数值规则。

**取消旧号与取得新号通常无法原子执行。**取消成功后仍可能停止放号、网络失败、授权失效或不满足资格，数据库事务不能消除此业务风险。优先验证是否存在官方换号能力；否则必须在允许的风险范围内设计失败处理与提醒。

请求超时或通信错误不等于取号/取消失败。需先核对本人号单，再决定是否重试。对结果未知的操作不能盲目重复，个人计划应有并发锁、操作日志和幂等/对账机制，禁止两个进程同时重排同一号码。

## 2.7 大语言模型职责

用户要求在自有算法中额外加入大语言模型进行实时计算。规划方式：

```text
外部信息更新 → 大模型提取结构化事件 → 来源/时间/字段校验
→ 更新有效特征 → 数值模型重新预测 → 生成可理解的解释与提醒
```

事件可包括商场活动、促销、营业调整和其他有来源依据的门店热度因素，记录地点、有效时间、来源和可信程度。天气与节假日优先使用可靠结构化来源，避免让大模型自行猜测。

大模型不编造叫号速度，不以自然语言猜测替代数值模型，不直接执行取消。按城市、门店和事件缓存分析结果，每次实时预测使用最新有效特征即可，避免每 30 秒为每位用户重复调用。

用有/无大模型特征的对照回测验证收益。手机号、业务凭证、个人二维码和个人号单等不发送给模型；未来选定模型服务、费用和数据处理配置后必须记录。

## 2.8 架构、运维与全国能力分级

服务器与产品的初步技术建议如下，**仍是规划**；当前先实现 Python 标准库 + SQLite 的本机只读验证工具，不代表已实现下面的服务架构：

| 模块 | 候选技术 | 目的 |
