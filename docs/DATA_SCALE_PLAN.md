# 历史数据增长与统计读取

2026-10-17 E0544，开发版0.3.0.dev1。以下已部署到原服务器，正式0.2.0安装包保持冻结。

## 选择的处理方式

原始采集归档继续完整保存。新增独立、可重建的统计读库，由后台持续增量更新；网页读取这个读库，不在每次打开时校验、汇总全部原始历史。

这采用了成熟系统的物化视图、增量维护和索引读取思路：[PostgreSQL物化视图](https://www.postgresql.org/docs/current/rules-materializedviews.html)把计算结果保存后提供查询；[ClickHouse增量物化视图](https://github.com/ClickHouse/clickhouse-docs/blob/main/docs/materialized-view/incremental-materialized-view.md)把新增数据的处理移到写入链路；[SQLite查询规划](https://www.sqlite.org/queryplanner.html)说明索引范围查询如何避免全表扫描。本站实际部署仍是SQLite，不声称已经安装PostgreSQL或ClickHouse，也没有为了参考架构增加云服务或付费依赖。

## 已部署的算法

1. 原始归档只读。按源文件与固定范围生成身份；持久记录原始记录、连续性包各自的rowid游标，只读取新增部分。
2. 新记录、后来补到的连续性链接和前驱只标记相应门店、日期为待更新。同一天的多次变化合并处理；单日复用原有完整校验与统计函数。
3. 用`(source_key, store_id, day, source_rowid)`索引定位单日原始行，再按原始rowid主键读取。用`(day, store_id)`索引读取所选月份；单店单日使用复合主键。
4. 提前保存月历摘要、日内明细、堂食与预约统计。每个门店每日最多1000条、单分区解压上限2MiB，摘要带SHA256，压缩包有长度和尾部检查。
5. SQLite WAL使网页只读事务与后台更新分离；分区发布与待更新标记删除在同一事务内完成。游标及索引也是事务提交，进程中断后从已提交位置续行。原始数据、失败和采集预算不会因此重置。
6. 每源每轮最多256条记录，通常约2MiB记录批次，最多16个有界连续性包；每轮最多发布32个门店日分区。有积压时继续分批处理，空闲每30秒检查一次。SQLite忙则退让，不能提前确认游标。
7. 网页按月或有界时间段查询。智慧分析默认最近30天，提供7天、一年及自定义，单次至多366个自然日；不再把起点固定在2026年10月1日而无限增加。全部旧数据仍保留，可分范围查阅。
8. 原有同请求合并、有界读取并发、固定容量缓存、静默刷新继续使用，文本传输启用gzip。查看页面不新增寿司郎GET，不把读取时间当成采样时间。

## 故障和容量保护

- 独立后台最多512MiB、最多一个CPU核的配额，低优先级、无网络、原始归档只读。当前83店、28个归档组；本版显式范围最多128家，不擅自扩大采集。
- 单组归档身份被替换、倒退或校验失败时隔离该组，其他健康组继续发布和读取。旧有效分区在新数据积压期间继续可读，保留真实观测时间；不把旧数据伪装成当前样本。原采集的单店隔离机制保持。
- 新增独立状态心跳。超过120秒无有效状态、汇总落后超过当前采样周期加120秒、持久源错误或网页服务退出进入现有邮件告警。告警不新增接收人，沿用QQ邮件、每日20次和去重规则。
- 可用磁盘低于5GiB或15%发容量提醒。容量预警不会隐藏仍然有效的统计数据，也不会删除历史记录。整机断网／断电无法靠同机服务发信，仍需后续独立外部监控。
- 没有把分表或删除当成当前急救措施。数据按日期索引，但原始库尚未物理按月分库，也未接入对象存储、消息中间件或分布式数据库。

## 后续扩容条件

当前解决的是历史增长引起的重复扫描与请求内计算，不承诺单机容量无限。

- 若积压在正常采样速度下连续无法清空，先读取待更新分区、单轮耗时、CPU／内存与磁盘证据，调整有界发布批量；不要无限增加网页并发或把压力传回官方接口。
- 长期原始归档增加时，按月只读封存并验证摘要、备份及跨月查询清单，再迁移冷归档到私有存储；不自动删除或改写原始账本。这一物理分区迁移尚未执行。
- 达到本版128家范围、持续高写入竞争或当前机器吞吐上限时，再迁移统计读库到PostgreSQL；需要跨年、全量复杂分析时评估列式分析库。切换前保留双读结果对照、可重建游标与回滚路径，不能仅因为数据量大就同时引入多套数据库。
- 预测特征从本读库的历史／日内摘要生成，原始精确到号证据仍从既有私有链路校验。模型预算用完与统计加载故障分开处理；本次未提高每日10元预算，也未修改预测算法口径。
