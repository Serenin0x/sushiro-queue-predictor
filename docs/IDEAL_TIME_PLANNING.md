# 理想用餐时间反推 · 完整候选评分

rc68增加后台研究算法 `idealplanning.py` 和私有命令 `ideal-time-research`。输入理想到店时间、叫号偏移和允许的提前／过晚范围，逐个比较明确的候选取号时刻。算法输出各候选的完整评分与研究建议；当前没有接入用户页面、自动取号或云端执行，实际叫号误差仍未校准。

## 时间与偏好

目标叫号时刻 = 理想到店时刻 + 有符号偏移。18:00到店、+10是希望18:10叫号；−10是希望17:50叫号。它们不是模型的预测误差。

另设可接受叫号窗口 `[目标−early_minutes, 目标+late_minutes]`，两个边界均包含。默认允许提前0分钟、过晚10分钟；用户偏好、模型不确定性、取号系统可用时段分别处理。候选来自调用方明确给出的完整时间网格，最多288项，严格递增，位于观测截止至其后一天；不假设更晚取号一定更晚叫号。

每个候选必须有相同门店、队列、观测截止和完整公共上下文，只接受新取号的**总等待**分布，不能混入已取号者的条件剩余等待。堂食／预约沿用[独立队列绑定](QUEUE_BINDINGS.md)。缺少模型的候选原位保留，整份输入先验证，再计算；不静默删项、截断或先发布部分建议。

## 为什么比较完整分布

只选“中位叫号最接近目标”的候选，可能忽略大量过早和过晚结果。例如一个候选49%很早、2%恰好、49%很晚，中位数碰巧准确，却不适合作为安心到店的依据。另一候选70%落在可接受窗口内，可能更符合用户偏好。

预测评分应与任务和决策目标相匹配，这一原则见 Gneiting 的原始论文 [Making and Evaluating Point Forecasts](https://arxiv.org/abs/0912.0902)。本项目的窗口质量界、阈值和候选排序为独立实现；论文不证明本项目的实际准确率或寿司郎业务规律。

对候选取号时刻 `t`，把叫号窗口换成等待窗口 `[a,b]`。每条等待区间 `[l,u]` 保留原次数，`u=null`表示较晚端未知：

| 事件 | 确定落入的条件，形成下界 | 可能落入的条件，形成上界 |
| --- | --- | --- |
| 提前 | u已知且u<a | l<a |
| 窗口内 | l≥a且u已知且u≤b | l≤b且（u未知或u≥a） |
| 过晚 | l>b | u未知或u>b |

先按原样本次数计算经验质量界，再按融合情景权重组合。原次数、区间原子和权重用精确分数计算，保留1/3等比例，不提前四舍五入到百万分率。上下界表达区间资料的不确定性，**不是经真实用户结果校准的总体概率或置信水平**。

默认要求窗口内下界至少60%、提前上界最多20%、过晚上界最多20%；这些是显式研究偏好，可修改，不是官方规则或防过号保证。先筛满足偏好的候选，再按窗口内下界从大到小、提前上界从小到大、过晚上界从小到大、取号时刻从早到晚排序。

输出保留全部满足偏好的候选，以及计算时刻尚未过去的子集。过去的最佳时刻仍可审计，但不会成为可执行建议。只有当前公共观测来自运行写者、接收时间在允许年龄内、上下文未过期、目标尚未过去时，才允许选出一个未来研究候选。否则保留“资料不足／偏好无法满足／候选已过时／当前观测不可用”。

## 历史、实时和AI怎样接入

`build_ideal_plan()`复用[历史区间桥接](HISTORY_FUSION.md)，按截止前本机首次收到的经历与审核记录选样，匹配门店、队列、人数／桌型及日期时段，保留退层、排除和输入摘要；不使用未来才收到的经历。当前命令只拟合history情景，`realtime_regime_models_fitted=false`。

`score_issue_grid()`可接收每个取号候选各自的完整多情景分布，允许后取号更早叫号。同一份可选公共AI建议分别通过每个情景集合的绑定、版本、有效期和权重校验，再参与[受限分布融合](DISTRIBUTION_FUSION.md)。私人取号时刻、人数、审核记录和等待分布不传供应商；本命令不会读取API密钥、请求模型或产生费用。只有history一个情景时，AI权重不会制造不存在的数值作用。

实际实时反向模型还需要正常用餐标签、未来新取号队列特征、时间顺序对照和区间校准。当前采集的展示曲线可以研究推进规律，不能替代准确发号时间、本人首次有效叫号或真实过号结果。

## 私有命令与输出

```sh
sushiwait ideal-time-research \
  --source-db source/outcomes.sqlite3 --reviews-db reviews/reviews.sqlite3 \
  --input plan.private.json --context-file context.private.json \
  --early-minutes 0 --late-minutes 10 \
  --minimum-window-mass-ppm 600000 \
  --maximum-early-mass-ppm 200000 --maximum-late-mass-ppm 200000 \
  --output output/ideal.private.json
```

计划使用[历史基线](HISTORY_BASELINE.md)的schema1、`mode=ideal_time`，含`desired_arrival_at`、`call_offset_minutes`及完整`candidate_issue_times`。公共上下文须schema2及现行队列策略。可选`--advice-file`只读已经生成的公共建议；`--ai-blend-ppm`默认0。输入计划／上下文／建议各16KiB以内，完整候选输入及结果最多2MiB；超限明确失败。

目录0700、文件0600；源库与审核库目录分开，输出另存。只读本任务闲置的经历／审核库，不读取或重启运行采集写者。结果不可覆盖，提交后持久确认状态单独报告；终端仅输出计数、选择索引和安全状态，不泄漏私人路径或经历ID。失败的`committed`字段反映文件是否可能已经提交，不能一概声称没写入。

输出包括完整候选、提前／窗口内／过晚的精确上下界、p10／p50／p90叫号包络、偏好、观测有效状态、原历史输入摘要与新评分输入摘要。未知较晚端保持null，不伪造时间。所有结果继续`eta_available=false`、真实认证标签0；连续建议时段、全局最优、放号可用性、真实叫号、总体概率及区间覆盖均未验收，通知和取号／取消动作均为0。

## 接手与完成条件

核心入口为`src/sushiwait/idealplanning.py`、CLI和`tests/test_ideal_planning.py`；安装检查也执行新的私有命令。专项覆盖全分布优于中位数、偏移符号、闭边界、未知上端、精确比例、潜在真值枚举、迟到／错误候选、非单调、过去最佳候选与完整288项网格、AI建议及私有首次接收流程。合成检查只验证算术与程序行为。

接到用户页面前，补充新取号实时情景拟合、营业／实际放号条件、随着新观测重新评分与撤回旧建议、两种模式的同时间切分回测，以及正常结果校准。设计内容遵循[DS-001](design/CONTENT_SPEC.md)；没有相应数据时显示暂不能建议，不能用CLI成功或测试数量宣称正式v1.0完成。
