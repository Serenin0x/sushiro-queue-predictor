# 持久共享匿名采集窗口

开发候选0.2.0rc31新增`remote-window-collect`、`remote-window-serve`和只读`remote-window-status`。与[固定任务](ANONYMOUS_TASKS.md)及[短时监控](ANONYMOUS_QUEUES.md)并存，不改变旧命令边界。它把原始截止时间、总预算、同店刷新进度与提交结果一起保存，供显式重启恢复；有界窗口实现不等于已完成24/72小时、全国或云端验收。实际证据见[交接记录](PROJECT_HANDOVER.md)。

## 配置与运行

明确提供1–3家店、私有计划文件、独立数据库和任务文件。基础间隔60–3600秒，窗口30–259200秒（最多72小时），总成对尝试预算1–25920。默认基础300秒、窗口86400秒、预算8640；这只是参数默认值，不证明允许长期频率。每对最多两次固定官方GET，失败立即停止、无重试；两条响应仍不是原子快照。

空计划用于背景采集，文件内容为`{"schema_version":1,"plans":[]}`。非空计划沿用[共享策略](SHARED_MONITORING.md)的字段和最多128份计划；同店取最紧迫的60/30秒目标，30/15分钟边界提前重算。没有活动计划的已选门店继续按基础间隔采集。计划中的既有`last_poll_started_at`必须缺省或为空，实际开始时刻由本任务保存，不能借用别的进程的进度。

以下路径仅为操作者自行准备的私有目录示例，计划文件0600，父目录0700；不能指向仓库，也不要放入真实账号材料。工具不自动创建用餐计划或请求微信授权。

```sh
sushiwait remote-window-collect --db /private/tmp/queue-window/remote.sqlite3 \
  --task-file /private/tmp/queue-window/task.json \
  --plan-file /private/tmp/queue-window/plans.json \
  --store-id 3014 --store-id 3004 --store-id 2009 \
  --base-interval 300 --duration 86400 --max-pairs 8640
```

需要展示时将命令换成`remote-window-serve`，安装可选`server`依赖。它沿用[号码服务](ANONYMOUS_SERVICE.md)的回环地址、单工作者、只读三路由、生命周期与停止规则。HTTP读取只看工作者公布的验证副本，不增加上游GET、不绕过数据库保护锁。任务截止、预算耗尽或失败后仍可展示旧信息，健康检查503；服务进程仍存在不代表采集仍在进行。

## 持久恢复与实际节奏

任务schema2、最多16KiB，与固定任务schema1分开；匿名快照数据库schema1不变。保存创建时间及原始UTC截止时间、数据库身份、配置、计划内容摘要、总预算、成功/失败/未知槽位、各店实际开始时刻、在途尝试和结果链摘要。任务0600、同目录原子替换/文件及目录确认、独占任务锁与数据库父目录保护沿用固定任务。

使用完全相同的参数，加`--resume-task`恢复。rc34另提供显式`--resume-if-present`，有任务才恢复，任务与数据库都不存在才新建；任务丢失但已有库停止，新库必须排他创建，见[Linux部署](LINUX_DEPLOYMENT.md)。不会重置截止时间、预算或未知槽位；原schema2的计划语义必须保持，空白格式变化若解析内容相同可接受，内容变化停止。rc40新任务可显式启用[版本化计划更新](MONITORING_PLAN_UPDATES.md)，支持固定范围内完整计划集合更新；不可升级旧任务或改变期限/预算，多用户认证和逐条计划日志仍待实现。

启动时核对任务后的全部已提交前缀，最多预算+2行；当数据库提交成功但任务确认中断，恢复只对账同一次结果，不再次查询。若在途结果没有保存，记为未知并消耗一个预算槽位；实际未记录HTTP数量保持unknown，不称零。失败及完成状态再次恢复不创建查询客户端或发请求。截止已经过去时先对账，再结束，不补查。

恢复后保守等待当前完整周期；若等待过程中进入15分钟窗口，按新30秒周期重算。周期由实际开始锚定，长缺口只查一次当前状态，不追赶遗漏请求。每对查询和持久提交占用时间，超过周期后也不会连发补齐历史。

进程内同时检查UTC墙钟和单调时钟，倒退停止；墙钟向前跳不能绕过单调最小间隔。单次运行将剩余UTC期限转换为单调上限，墙钟变慢时以`monotonic_duration`结束。单调时钟不能跨进程/系统重启保存；跨重启仍依赖系统UTC准确和保存的原始截止时间，不能承诺错误系统时钟下的精确现实总时长。截止和预算限制新的成对尝试登记，在途一对允许结束，实际最后接收可能晚于截止，不能将接收时间当新请求起始。

运行时检查数据库身份、大小/修改时间及SQLite data_version，私有计划重新读取并核对摘要；追加结果与任务确认后更新守卫。每次仅查尾部，不每30秒重复扫描全天历史；外部提交或文件替换使任务停止。完整历史链在启动恢复时再次核对。不能把合作锁描述为阻止任何外部工具强行写数据库的权限系统。 持久文件身份采用设备与inode，内容另核完整结果链；[Python stat说明](https://docs.python.org/3/library/os.html#os.stat_result.st_ino)限定该属性的身份语义，不能将它称文件删除后永不复用的代际ID。替换测试先并存两文件确认身份不同，再原子替换；同身份且相同已验证内容的重建不能据此认证发生过替换。

## 状态、缺口与边界

`remote-window-status --task-file ...`只读检查保存状态，不读计划、不打开数据库、不联网、不检查进程存活。输出原截止、预算、已消耗槽位、已记录HTTP数量和最近缺口；不输出私有路径、计划摘要或每人的到店时间。`last_gap`是最近缺口摘要，全部观测时间由私有数据库保留，不是完整停机审计日志。号码服务另给工作者实际存活与最后公布检查点，可能落后在途操作。

原始数量单位、源更新时间、门店身份和刷新时效保持unknown；成功GET或新接收时间不能认证源刚更新。verified_training_labels=0、eta_available=false；60/30秒调度不等于防过号提醒或两种预测已经完成。原schema2没有热更新计划；rc40新任务的显式更新见上述说明。无限守护、自启重启、自动恢复失败任务、云端HTTPS/访问控制、用户前端及取号/取消/重排仍未完成。停止/中断和质量缺口应保留，不能通过不断创建新窗口绕过原期限或预算。

实际安装包的中断恢复、HTTP展示与截止已有下节短时证据；rc40运行中修改计划的真实接口证据见[计划更新验证](MONITORING_PLAN_UPDATES.md#独立安装版的真实接口验证)。原三店24小时任务按既定期限运行，待自然终态后进行只读完整质量分析。24/72小时验收分别记录真实开始/结束、失败、缺口、源变化和覆盖，不用合成时钟或旧两小时成绩替代。服务器环境、源语义、可信叫号结果与预测误差仍分别验收。

终态窗口新增[完整质量报告](ANONYMOUS_WINDOW_QUALITY.md)：在打开库前拒绝未完成任务，核对全部结果链、日期分布与开头/尾部/内部缺口，区分预算完成和截止完成；不认证源新鲜度或真实叫号标签。

## 本版实际验证

初rc31安装包实际查询中关村3014：首进程数据库提交后在任务确认前退出，第二进程恢复同一任务；三对六GET全部200，实际起始间隔59.958与30.009秒，共90.834秒。两份合成时间计划用于测试调度，非本人真实用餐或训练标签；第一份保存结果不重查，原截止与预算保持。恢复采集时五次实际HTTP展示新增上游请求0，数据库保护锁保持；完成健康503，完成任务再开只展示历史、查询客户端0、库/任务/计划字节不变，全部服务实际停止。与rc27两小时、rc28及rc29试验各用独立库，不累计冒称24小时。详见E0237。

rc40独立121.340秒实测接受三次计划更新，3对6GET全200、开始间隔60.011/30.009秒，前五次HTTP读取新增上游请求0；到期及终态文件保护通过。合成计划输入与真实网络分别记录，3行终态质量链已核，但连续验收仍为false，不混入原rc31三店全天任务。详见交接E0268。


## 合盖与计时检查

用户电脑在合盖、远程连接期间，具体采集进程仍可存活，但进程存活、成功请求数和检查点`last_gap=null`不能认证全程没有睡眠或采样空窗。2026-10-07恢复时，原任务的UTC跨度与私有进度保存的单调计时已有差值；只作为诊断，不能直接将差值当停机时长或猜测唯一原因。原期限和预算保持，不重启或补抓。自然终态后按逐店实际请求时间核对开头/内部/尾部缺口，连续性结论与源刷新时效分别验收。
