<p align="center"><strong>少一点盯号，多一点自由安排。</strong></p>

想吃寿司，却不知道还要等多久、该几点出发、会不会突然过号？SUSHIWAIT 希望把实时号码、历史规律和日期差异串起来，让用餐计划更有依据。

这是面向中国大陆寿司郎门店的独立开源项目。目前已有 **12 家门店的云端营业时段采集和只读统计页面**；源码同时提供已有号码的参考时间实验。真实等待误差尚在校准，正式 v1.0 继续开发。

## 产品功能

- **把排队变化看清楚**：保存每次查询时间、各队列原有顺序的前三个展示号码、原始数量和错误状态。按门店查看号码与时间曲线、展示变化速度，页面每 30 秒读取已保存的数据，多人查看共用后台采集。
- **让每天的数据留得住**：浅色月历按店铺、日期查看统计，颜色先表示采集覆盖。按营业日自动接续的控制器每天独立保存任务、原始库和归档，闭店等待、次日再采；可读取历史月份，缺失与损坏分别报告；整月归档在后台校验，先显示已完成的统计与加载进度；旧试采副本按明确日期只读接入，保留原时间与曲线。新增[日质量报告](docs/DAILY_SAMPLING_QUALITY.md)，区分请求开始与响应接收，记录断档与失败。**云端每日接续已安装，等待今晚闭店交接及明天开采。** 详见[每日采集与归档](docs/DAILY_COLLECTION_LIFECYCLE.md)。
- **输入已有号，跟上最新趋势**：源码中的[号码参考实验](docs/REFERENCE_POSITION_RESEARCH.md)根据近期推进和突然加速重算参考到达时间；观测陈旧、失败或参考倒退时暂停。号码和取号时间只留在浏览器内存。当前结果是展示位置的快慢情景，还不是已校准的实际叫号误差；云端页面尚未部署此实验。
- **把历史与实时接起来**：已有历史区间、条件剩余等待、实时邻域与时间顺序回测工具，支持区分普通／预约、星期、节假日、月份和季节。资料不足保留未知，不把号码差当精确前方桌数。方法见[核心范围](docs/V1_CORE_SCOPE.md)和[实时模型回测](docs/REALTIME_BACKTEST.md)。
- **让 AI 帮忙判断变化**：已有[DeepSeek 适配与调用预算](docs/DEEPSEEK_ADAPTER.md)、候选分布与权重融合工具。同店公共建议可以共享，重复观测不重复调用，异常回退本地计算。尚未配置付费调用，实际精度收益仍需对照验证；个人号单和凭证不发送给模型。
- **为真正的等待误差积累依据**：支持私有保存本人正常用餐的签到、叫号、入座等[经历草稿](docs/EXPERIENCE_RECORDING.md)，保留时间范围、修订和接收时刻。展示号码消失不会自动成为“过号”，历史回放也不会使用当时尚未收到的信息。

核心 v1 接下来继续完成：历史初估与实时预测、可解释的误差范围、理想用餐时间反推，以及临近到店的 60／30 秒监控与防过号提醒。自动取号、取消和重排保留为后续阶段；逐号发放时刻先做[接口研究](docs/TICKET_ISSUANCE_RESEARCH.md)，不在v1.0部署。

## 技术手段

使用 Python 3.11+、固定 HTTPS 只读请求、SQLite 和轻量网页。匿名门店查询与正常微信凭证查询分开；每日任务使用独立锁、原期限与预算、有限退避恢复和不可覆盖归档，查看统计不会新增寿司郎查询。营业时间缺少单店资料时，采用用户指定的假定：周一至周五 11:00–22:00，周末或已知节假日 10:30–22:00，可按门店覆盖。

预测采用可计算的历史／实时模型，再结合受限的大模型建议，按时间顺序比较结果。完整数据数组仍保存在原始库；前三位曲线是展示观测，第一位只是用户约定的叫号参考。来源新鲜度、部分数量单位、实际叫号／过号和全国覆盖继续核验。

**前端设计板块**：[页面、流程与内容规范](docs/design/README.md)。供独立设计GPT接手，包含页面清单、字段含义、预测与提醒状态、日历曲线和隐私边界；视觉样式另行设计，当前能力与未来计划分别说明。
