## 产品功能

- **把排队变化看清楚**：保存每次查询时间、各队列原有顺序的前三个展示号码、原始数量和错误状态。按门店查看号码与时间曲线、展示变化速度，页面按后台采集频率同步已保存的数据，按工作日、普通周末和节假日分别设置平峰／高峰频率，前后30分钟连续过渡；自动更新保留页面位置、号码和曲线，只更新有变化的数据，多人查看共用后台采集。
- **让每天的数据留得住**：新月历支持浅深色、城市和门店筛选，按日期查看真实统计，颜色先表示采集覆盖。按营业日自动接续的控制器每天独立保存任务、原始库和归档，闭店等待、次日再采；此前保存的10月9日、10月10日记录已合入同一个月历，直接按日期查看；门店曲线继续分来源，避免拼出不存在的连续轨迹；可读取历史月份，缺失与损坏分别报告；整月归档在后台校验，先显示已完成的统计与加载进度；旧试采副本按明确日期只读接入，保留原时间与曲线。新增[完整原始备份与恢复](docs/DAY_BACKUP_RECOVERY.md)，保留原时间、完整数组和任务证据；恢复到新目录重新读取曲线，不覆盖正在采集的数据。新增[日质量报告](docs/DAILY_SAMPLING_QUALITY.md)，区分请求开始与响应接收，记录断档与失败。**新月历已在原统计地址上线，旧147店已保存28,604组记录；10月10日13:53匿名通道HTTP403保护停采。10月11日新三店官方记录已回到原统计页，低频新观测自动同步；旧缺口保留。** 详见[每日采集与归档](docs/DAILY_COLLECTION_LIFECYCLE.md)。
- **输入已有号，跟上最新趋势**：线上[已有号跟踪](docs/EXISTING_TICKET_LIVE.md)在同店历史足够时先给初估，随后按新观测调整；不同星期、日期类型和时段分层选取历史，突然加速会提高近期变化的影响。资料不足时保留实时趋势，较晚时间无法确定时直接说明；观测陈旧、失败或参考倒退时暂停。未提交内容留在浏览器草稿；选择录入后通过HTTPS保存到本人服务器私有库，不发送给模型。号码进入原展示前两位即判到号，三位全部越过则记推定到号，未签到也可形成等待参考。当前结果是展示位置的快慢情景，还不是已校准的实际叫号误差；可从时钟入口打开工程页，再选择“预测与记录”或“我的号码”；工程页按门店监测、智慧分析、预测与记录、我的号码、用餐记录分类查看；[号码记录库与智慧分析](docs/ENGINEERING_ANALYTICS.md)支持本人记录分页、号码搜索和排序、CSV导出，以及历史覆盖、时段热力图、城市观测分布、本人取号样本缺口建议和可手动刷新的智能分析；数据准备度不冒充预测准确率，展示信号不冒充实际人数；城市与门店分两级选择，图点、采样表和详情联动，切换保留输入和浏览位置；rc76已把该页面和历史读取绑定到新官方来源。当前低频记录缺少连续性证据时说明不足，最新原号码出现提示独立更新；该官方接线已在原服务器地址部署。源码新增[匿名连续性导出](docs/OFFICIAL_CONTINUITY.md)，区分分页前序、写者切换、失败和断档；新合同已接入独立云归档和原统计页，缺口不补造速度；当前十分钟观测用于长期验证，资料较旧时历史曲线继续可看、顶端号码暂停展示。
- **看见变化，及时准备到场**：源码增加[页面风险提示](docs/REFERENCE_PRECAUTIONS.md)，关注本人号码是否进入展示列表、参考是否加速或提前，以及计划到店是否赶得上较早情景。数据失效就暂停判断，提示只在页面打开时更新；后台推送和真实过号概率仍待接入。
- **把历史与实时接起来**：已有历史区间、条件剩余等待、实时邻域与时间顺序回测工具，支持区分普通／预约、星期、节假日、月份和季节。资料不足保留未知，不把号码差当精确前方桌数。方法见[核心范围](docs/V1_CORE_SCOPE.md)和[实时模型回测](docs/REALTIME_BACKTEST.md)。
- **按理想时间安排取号**：新增[完整候选反推算法](docs/IDEAL_TIME_PLANNING.md)，把希望几点到店、希望早叫或晚叫几分钟、可接受的时间范围分开，逐个比较候选取号时刻的提前与过晚风险；资料不足或时机已过就保留无法建议。当前为后台研究工具，尚未接用户页面或校准实际叫号误差。
- **让 AI 帮忙判断变化**：已有[DeepSeek 适配与调用预算](docs/DEEPSEEK_ADAPTER.md)、候选分布与权重融合工具。同店公共建议可以共享，重复观测不重复调用，异常回退本地计算。DeepSeek Flash思考／非思考已经真实接通，同店新观测自动生成共享情景建议，最多影响30%的融合权重；实际精度收益仍需对照验证。个人号单和凭证不发送给模型，网页选模式不重复付费。
- **为真正的等待误差积累依据**：新增[截图录入](docs/SCREENSHOT_IMPORT.md)，拖入或批量选择截图，识别结果填入可编辑表单，城市、门店、号码与取号时间均可修改，手动时间填到分钟即可。预测在提交前选择模型；批量记录提交成功自动清空，失败项保留重试。重复记录自动合并，识别在自有服务器完成，无需额外模型API。支持在浏览器记录、下载与恢复本人正常用餐的取号、签到、叫号、入座等[经历草稿](docs/EXPERIENCE_RECORDING.md)，保留时间范围和完整修订；另有私有接收命令保存实际首次接收时刻，不自动审核。展示号码消失不会自动成为“过号”，历史回放也不会使用当时尚未收到的信息。

核心 v1 接下来继续完成：历史初估与实时预测、可解释的误差范围、理想用餐时间反推，以及临近到店的 60／30 秒监控与防过号提醒。自动取号、取消和重排保留为后续阶段；逐号发放时刻先做[接口研究](docs/TICKET_ISSUANCE_RESEARCH.md)，不在v1.0部署。

## 技术手段

2026-10-15 当前进度：**五店每日采集继续运行，QQ邮箱异常提醒与受限授权入口已接通**。17:42健康状态正常，最近17:40新样本，当天75组成功、失败0。每个营业日独立保存，午晚高峰3分钟、其它10分钟并连续过渡，旧缺口保留。邮件提醒可打开原账号授权页，正常确认后由后台接续；本人已确认测试邮件收到、Safari显示与系统保存二维码成功。微信仍要求摄像头现场扫码，需要另一块屏幕；真实故障后的完整自动恢复继续等待自然验证。详见[每日采集](docs/RECURRING_COLLECTION.md)、[会话与提醒](docs/AUTH_SESSION_ALERTS.md)。

使用 Python 3.11+、固定 HTTPS 只读请求、SQLite 和轻量网页。 统计采用[增量读库和日期索引](docs/DATA_SCALE_PLAN.md)，后台只更新变化的门店日，网页读取预先生成的汇总；历史增长不再导致每次全量扫描，容量不足与汇总异常接入现有邮件提醒。截图使用自有服务器的RapidOCR与PP-OCRv5轻量CPU模型识别，私人录入走HTTPS。匿名门店查询与正常微信凭证查询分开；每日任务使用独立锁、原期限与预算、有限退避恢复和不可覆盖归档，查看统计不会新增寿司郎查询。营业时间缺少单店资料时，采用用户指定的假定：周一至周五 11:00–22:00，周末或已知节假日 10:30–22:00，可按门店覆盖。

官方凭证自动供应已有实际进展：[本机隔离实验](docs/YYB_LOCAL_TRIAL.md)完成正常本人认证、无人取码与六次凭证更新，原读者持续查询三店。10月12日，固定云实例、私有初始化材料和正常云会话已部署，首次云初始化与三店查询成功，公共记录自动接入原统计页。供应和查询凭证留在私有服务器，管理入口仅回环访问；正常微信重新认证仍可能需要本人操作。五店已使用午晚高峰3分钟、其它10分钟及连续过渡；每日持续运行替代旧有限试验，历史失败与账本保留。不能把首次云查询成功当成多日稳定或永久无需人工认证。

预测采用可计算的历史／实时模型，再结合受限的大模型建议，按时间顺序比较结果。完整数据数组仍保存在原始库；前三位曲线是展示观测，第一位只是用户约定的叫号参考。来源新鲜度、部分数量单位、实际叫号／过号和全国覆盖继续核验。

**前端设计板块**：[页面、流程与内容规范](docs/design/README.md)。供独立设计GPT接手，包含页面清单、字段含义、预测与提醒状态、日历曲线和隐私边界；视觉样式另行设计，当前能力与未来计划分别说明。
